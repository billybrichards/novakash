Headline answers

  • Why are 15m predictions "dodgy"? Three stacking issues: (1) per-asset feature cache only seeds BTC, so ETH/SOL/XRP cold-start; (2) the 15m classifier head 15m_head_v1 is a v1-style architecture (input_dim=1280, no v2 close-relative features) trained 2026-04-20 — the better v2-class architecture exists but wasn't ever 15m-specific; (3) the per-timescale classifier dispatch on the GPU box returns bit-identical values for 5m and 15m, suggesting only one head is producing the outputs (audit #342).
  • Why was cls_traj_14f_iso never promoted? Per note #263 (2026-04-25): "Head trained on broken pipeline surfaces. Needs full retrain with model_id fix." The model_id fix landed in PR #131, but no retrain happened after. The current GPU-box head IS cls_traj_14f_iso, but its training-time TimesFM surfaces were wrong. It needs a clean retrain post-PR #131 before live-primary promotion.
  • What's v12-XL? v12-XL = v12 architecture + 112 features (v10 schema) + nested_5m_* aggregations + isotonic-per-horizon calibration. It's the latest 5m LGB candidate (Today 00:03 UTC, val T-90 acc 78%). For 15m we need to clone this architecture but train on 15m labels — that's the highest-leverage retrain available (single biggest WR-ceiling lift for 15m).

5. The cls_traj_14f_iso decision — why never promoted

What it is

Best classifier head we've ever trained:

  • 14-feature trajectory architecture (vs unified's pure quantile surface)
  • Isotonic post-hoc calibration (88 knots)
  • Val dir_acc 72.86% overall, 79.85% on high-confidence band (HC coverage 65.2%)
  • ECE 5e-9 — essentially zero calibration error on holdout
  • Trained on Tiingo prices (matches Polymarket Chainlink oracle)
  • S3: path1_classifier/2026-04-25T15-34/cls_traj_14f_iso/
Why it's NOT live primary — direct quote from note #263 (2026-04-25), "Known issues" section:
"UP bias: pc=0.50-0.57 always. Head trained on broken pipeline surfaces. Needs full retrain with model_id fix."

Decoded:

  • The training pipeline had model_id=None, meaning the training script used a default/unspecified TimesFM checkpoint that produced quantile surfaces DIFFERENT from what the production deploy uses.
  • The classifier head learned to map THAT (incorrect) surface distribution to outcomes. When deployed against the CORRECT surfaces, its outputs are biased — pc=0.50-0.57 always (drifting near uncertainty).
  • PR #131 (commit 481f7d4 area, Apr 25 06:51) fixed model_id. But cls_traj_14f_iso was trained at 16:34 the same day — AFTER the PR #131 fix.
  • The note warns of "broken pipeline" — which suggests OTHER pipeline issues persisted past PR #131. Possible candidates: feature alignment, regime vocab, eval-offset, Tiingo backfill warmup.
  • Bottom line: It was never validated against PRODUCTION traffic. Note #190 even has a separate retrain plan ("focal loss + label smoothing + logit-L2") that's been "AWAITING post-hoc calibration results + user go/no-go" since 2026-04-19.
What this means for promotion: Don't promote cls_traj_14f_iso to live primary blindly. Instead:
  1. Validate it against current production data (24-48h shadow A/B vs unified_head/) — does the UP bias persist?
  2. If bias persists: do the retrain plan from note #190 (focal loss + label smoothing + logit-L2 + clean pipeline).
  3. If bias is gone (post-PR-#131 surfaces are now stable): promote.

7. Per-timescale dispatch — the bit-identical bug

Live diagnostic on the GPU box:

  { "15m": 0.38608115911483765 }    ← BIT-IDENTICAL to 17 decimals

Both 5m and 15m heads are CONFIRMED loaded (from container startup logs):

                          from /var/lib/novakash/timesfm_classifier/cls_traj_14f_iso (input_dim=1304)

                          from /var/lib/novakash/timesfm_classifier/15m_head_v1 (input_dim=1280)

Code review (forecaster.py)

The architecture is correct on paper. Per-timescale heads are stored in self.classifier_heads: dict[str, Module], configs in self.classifier_configs: dict[str, dict]. Two distinct env vars (TIMESFM_CLASSIFIER_HEAD_URI for 5m, TIMESFM_CLASSIFIER_HEAD_URI_15M for 15m). Lines 593-756 of app/forecaster.py loop over each loaded head and produce per-timescale outputs into by_timescale: dict[str, float].

Hypothesis for the bug (needs runtime verification):
  1. 5m head is v2 close-relative (input_dim=1304, has version: "v2_close_relative") → enters the v2 branch with dedicated forward pass using Tiingo prices + 512×2s subsample + base model (no LoRA).
  2. 15m head has input_dim=1280, no version field → does NOT enter v2 branch. Goes into v1/specialist branch.
  3. The v1/specialist branch uses the BASE forecast (line 641-647: head_preds = out.full_predictions[0, :head_horizon, :]) without v2's dedicated pass.
  4. For 15m's specialist case, head_horizon = 1280 / 10 = 128 — same as 5m's v2 head's flat surface.
  5. Possible cause: the v2 forward pass's output for the 5m head IS being CACHED somewhere keyed only by base inputs, and the 15m head's call inadvertently retrieves the same cached values. OR: the by_timescale dict population conflates because by_timescale[ts] = by_delta.get(60, ...) picks the same delta-60 value from a SHARED forecast surface for both heads.
Actual root-cause confirmation requires reading the forecast cache logic and instrumenting the GPU box. Tracked as audit #342.
Why this doesn't break v15m_up_basic in production today: v15m_up_basic reads probability_up (the BLEND), not probability_classifier directly. The BLEND is dominated by probability_lgb for 15m. The classifier component is buggy but its weight is small. Strategies that DO read classifier directly (v7_15m_sniper) ARE affected.
