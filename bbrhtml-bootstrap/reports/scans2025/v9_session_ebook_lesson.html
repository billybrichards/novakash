Chapter One

What We're Building

Six boosters, six calibrators, three assets — all routing on a single clock signal at serve time.

The v9.2 family is a collection of LightGBM classification heads trained to answer one narrow question for each five-minute Polymarket window: will the price of this crypto asset be higher or lower than the strike at expiry? Each "head" covers a specific delta-bucket — Δ1 (windows closing in 0–5 min) through Δ6 (25–30 min) — so the model that fires depends entirely on how many seconds remain at prediction time.

Per asset (BTC, ETH, XRP) the system trains six LightGBM boosters, each paired with a sklearn IsotonicRegression calibrator fitted on a held-out development split. The raw booster output is a monotone probability-like score; isotonic post-fitting bends that score into a true posterior that honours the empirical reliability curve. At serve time the serving layer routes the raw score through its matching calibrator before any threshold check fires.

The threshold is strict by design. p ≥ 0.96 to fire UP; p ≤ 0.04 to fire DOWN. Most windows are ignored entirely.

Production shadow config, 2026-05-19

At those extreme thresholds the live system aims for 22–74 fires per day across the three assets, at a $5 GHOST shadow budget. The win-rate at p ≥ 0.96 historically sits around 93–95%, well above the 50% naive baseline, but the calibration work is what makes that number trustworthy rather than just lucky.

Chapter Two

The Backfill Saga

No data, a race condition, 992 thousand duplicates, and a microsecond timestamp twist.

When the ETH and XRP training pipeline first ran, it hit an immediate wall: ticks_binance contained only BTC rows. Production had been persisting live Binance aggTrade data for BTC since the system launched, but ETH and XRP had never been plumbed in. The training code could not even begin building the 49 non-LoRA features without raw tick history.

The solution was to reach directly for Binance's public data archive at data.binance.vision. Every trading day is published as a gzip-compressed CSV with eight columns: aggregate-trade-id, price, quantity, first/last constituent trade ids, a Unix timestamp, is-buyer-maker flag, and best-price-match flag. One file per day per symbol, reliably available within a few hours of close.

Python — data.binance.vision URL pattern 
# data.binance.vision daily zip pattern
url = (f"https://data.binance.vision/data/spot/daily/aggTrades"
       f"/{symbol}/{symbol}-aggTrades-{date_str}.zip")
# CSV cols: agg_trade_id, price, quantity, first_trade_id, last_trade_id,
#           timestamp_us, is_buyer_maker, is_best_price_match
# IMPORTANT: timestamp column is in MICROSECONDS not ms (Binance switched mid-May 2026)
ts_seconds = ts_raw / 1_000_000 if ts_raw >= 1e14 else ts_raw / 1_000

The first agent backfilled the range 2026-04-29 through 2026-05-10 — eleven days of ETH and XRP history. But a second agent was spawned concurrently before the first confirmed completion. Both agents successfully downloaded and inserted rows from overlapping date ranges, leaving 992,492 exact duplicate rows in the ETH partition.

Root Cause

Two agents hitting the same idempotency gap: no unique constraint on (ts, asset, price, quantity, is_buyer_maker), and no transaction-level lock preventing concurrent inserts for the same date range.

The deduplication strategy was a windowed ROW_NUMBER() — keep the smallest id (first insert wins) and delete the rest. Applied per-date to keep the operation bounded:

SQL — Race-condition dedup 
-- Race-condition dedup
DELETE FROM ticks_binance
WHERE id IN (
    SELECT id FROM (
        SELECT id, ROW_NUMBER() OVER (
            PARTITION BY ts, price, quantity, is_buyer_maker
            ORDER BY id
        ) AS rn
        FROM ticks_binance
        WHERE asset = 'ETH' AND ts::date = '2026-05-07'
    ) sub WHERE rn > 1
);

After dedup, the second half of the backfill (May 11 through May 20) ran with one further wrinkle: Binance silently changed the timestamp column from milliseconds to microseconds sometime in early May 2026. The auto-detect heuristic — if ts_raw >= 1e14, divide by 1,000,000 — handles both epochs cleanly.

A final asyncpg type coercion issue slowed the insert: Python string dates could not be passed as ::date parameters; datetime.date objects were required. The same applied to timestamptz columns expecting datetime.datetime. After those fixes, the final row counts stood at ETH 12.2 M rows, XRP 2.3 M rows, 21 days of coverage.

Chapter Three

The Five-Stage Pipeline

BUILD joins raw tables into a feature matrix. TRAIN slices it into six delta-buckets and fits a booster per bucket. TEST sweeps decision thresholds. ECE audits calibration error. ISO fits the corrective layer.

Every v9.x model runs through the same five stages in sequence. Skipping any stage produces either an untrained model or an uncalibrated one — both are dangerous in a real-money shadow position.

Stage 1 — BUILD

Entrypoint: training.build_dataset. This stage performs a multi-table join across ticks_v2_probability, ticks_binance, ticks_chainlink, ticks_tiingo, and ticks_coinglass, then computes the 49 structured features (momentum, volume profile, order-book pressure, funding rate, etc.) in pandas. The result is a labelled feature matrix written to a local parquet file.

Fig 1 — BUILD: multi-source join → 49-feature matrix → parquet

Stage 2 — TRAIN

Entrypoint: training.train_lgb_v5. The feature matrix is split into six Δ-buckets by seconds_to_close. Each bucket trains an independent LightGBM classifier on a 70/15/15 train/dev/test split. The dev split is reserved for the ISO calibrator (below). Hyperparameters follow the v9.2 defaults; no AutoML sweep is run unless explicitly requested.

Fig 2 — TRAIN: one LightGBM booster per Δ-bucket, all trained independently

Stage 3 — TEST

After training, the held-out test split is swept over a range of decision thresholds (0.50 → 0.96 for UP, 0.04 ← 0.50 for DOWN). At each threshold the pipeline records win-rate and fires-per-day. The key trade-off: every notch toward the extreme recovers ~1–2 pp of WR but halves (or worse) the fire count.

Fig 3 — TEST: win-rate (green) climbs as threshold tightens; fire count (blue bars) drops sharply

Stage 4 — ECE

Expected Calibration Error measures how far the model's predicted probabilities stray from the true empirical frequencies. A perfectly calibrated model's reliability diagram lies on the y=x diagonal. Raw LightGBM scores almost never do — they cluster near 0.5, and the extreme tails are either overconfident or under-confident.

Fig 4 — ECE reliability diagram: red dots show raw LGB offset from perfect diagonal (dashed)

Stage 5 — ISO

Isotonic regression is a non-parametric monotone function fitted from raw booster scores to true-frequency labels on the dev split. It is strictly monotone — if raw score A > raw score B, then calibrated A > calibrated B — so ranking is preserved. At serve time every raw booster output passes through its matching isotonic regressor before threshold comparison.

Python — Isotonic post-fit 
from sklearn.isotonic import IsotonicRegression
iso = IsotonicRegression(out_of_bounds='clip', y_min=0.0, y_max=1.0)
iso.fit(dev_raw_p, dev_labels)
# At serve: calibrated_p = iso.predict([raw_p])[0]
Fig 5 — ISO: isotonic curve (green) departs from identity to correct tail miscalibration

Chapter Four

The Indicator & Curve-Shape Trial (BTC)

Adding 30 classical TA features to the 58-feature v9.2 baseline — and finding the conservative tail got worse.

The hypothesis was straightforward: RSI, MACD, KDJ, Bollinger Bands, and a set of EMAs over the 5m OHLCV series should carry signal orthogonal to the existing 49 structural features. To stress-test the shape rather than just the level, each indicator was augmented with five derivative features: a recency-weighted signed integral over 314 candles, first and second discrete derivatives, and positive/negative area-under-curve measures.

The trial pipeline aggregated ticks_binance BTC to 5-minute OHLCV, ran pandas-ta to compute the base indicators, then appended the shape columns — 30 new features total. Both baseline (58 features) and trial (88 features) were trained on the same 19-day window with the same hyperparameters, then compared on a held-out tail.

Verdict — SKIP

Win-rate delta at p ≥ 0.96: −1.60 pp. The conservative-tail precision suffered. Calibration actually improved (ECE dropped by 0.0108), but for a threshold-gated strategy, precision beats calibration. RDS note #560.

If you size on calibrated probability, the trial model is the better sizer. For conservative-threshold firing, the baseline wins.

Hub note #560 — Kelly framing of the indicator trial

The Kelly interpretation is subtle but important. A Kelly bettor weights position size by edge / odds derived from the calibrated posterior. The trial model's lower ECE means smaller systematic errors in that posterior — so a Kelly sizer would compound faster with the trial. But the current system does not size by Kelly; it fires a flat $5 shadow bet when a threshold is crossed. In that regime the threshold-precision metric dominates, and the baseline's −1.60 pp advantage at p ≥ 0.96 is the deciding number.

Chapter Five

The v9.3 ETH Attempt

21 days of raw ticks vs 8.2 days of pre-computed features — and a LoRA GPU job running in the background to bridge the gap.

The backfill gave us 21 days of ETH raw aggTrades — more than twice the 8.2-day coverage that ticks_v2_probability (TVP) offered for ETH. The question was whether the extra data was worth the reconstruction cost.

Three paths were mapped out. Path A: just retrain on TVP with its existing 29 features, gaining 26% more rows. Path B: reconstruct the 49 non-LoRA features from raw ticks (momentum, volume, OI, funding rate, chainlink, tiingo) — full 49 features but no tfm_* columns. Path C: reconstruct 49 AND run LoRA inference offline to generate the 9 tfm_* transformer features — full 58 features on the extended 20-day corpus.

Choice

Path C was chosen and parallelised: one background agent runs LoRA inference on the local RTX 3060; another rebuilds the 49 features from raw ticks, then joins the LoRA parquet, then trains baseline (v9.2-recompute, 8.2d) vs trial (v9.3, 20d). Verdict in flight as of session end.

The LoRA inference setup

The transformer features come from a fine-tuned google/timesfm-2.5-200m-transformers model. A PEFT LoRA adapter lives at /tmp/lora_adapter/ and a v2 trajectory classification head at /tmp/classifier_head_5m/. For offline inference, the script loads the base model, merges the LoRA weights, attaches the classification head, and runs batch inference over rolling 60-bar windows of ETH price/volume data. The output is a parquet file of per-window tfm_* activations, timestamped to join back onto the feature matrix.

PathCorpusFeaturesStatus
A — TVP retrain 8.2d +26% 29 Fallback
B — Raw ticks (no LoRA) 20d 49 Partial

The honest uncertainty here: LoRA inference takes ~40–60 minutes on the 3060 for 20 days of ETH, and the feature-reconstruction agent needs to wait for that output before training. The comparison point — v9.2-recompute on 8.2 days — was designed to isolate the corpus-size effect from any feature-reconstruction noise.

Chapter Six

Recurring Pattern: SSM Tunnel Survivability

Never fetch more than ~100k rows through a tunnel. Use server-side COPY instead.

The AWS Systems Manager (SSM) port-forward tunnel provides authenticated access to the RDS instance without opening a security-group hole. It is excellent for low-volume queries. It is treacherous for bulk reads. This session hit the wall three times in different forms, all rooted in the same limitation: the SSM tunnel's TCP keep-alive and protocol timeout sits around 10 minutes, and asyncpg's bind_execute protocol phase for a 12-million-row query comfortably exceeds that.

Anti-pattern

Calling asyncpg.conn.fetch() on a query that returns 12M rows. The connection hangs silently at the bind_execute phase, then drops after ~10 minutes with a transport error — long after the calling process has stopped printing progress.

Two fixes that consistently worked in this session:

Option A — data.binance.vision direct download. For raw aggTrade history, bypass the database entirely. The public archive is ~70 seconds per daily file on a typical connection. No tunnel, no auth, no timeout risk.

Option B — psql \COPY to local CSV. For data that is already in RDS, a server-side COPY TO STDOUT streams bytes in Postgres's native binary/text protocol. The tunnel sees a long-lived but active stream (bytes flowing continuously), which keeps keep-alive timers reset. Wall-clock time for 12M rows: 5–10 minutes. Then load from CSV into pandas or DuckDB locally.

The rule is simple: if your query returns more than ~100,000 rows, do not use asyncpg.fetch() through the tunnel. Use \COPY or a direct download.

Lesson crystallised from three independent tunnel failures this session

A third option — server-side cursor with small batches — works in principle but requires the consuming code to handle partial results and resume correctly. For one-off analytical runs, the psql COPY approach is simpler to audit and debug.

Chapter Seven

Recurring Pattern: asyncpg Type Strictness

The 'str' object has no attribute 'toordinal' error fires precisely when you pass a Python string where asyncpg expected a typed date or timestamp.

This error message is not immediately obvious: it comes from Python's datetime.date interface — asyncpg internally calls .toordinal() on whatever you pass as a ::date parameter, expecting a real datetime.date object. A raw ISO string like '2026-05-11' does not have that method, so the error surfaces.

The error appeared three times during this session, in three slightly different forms:

Case 1 — ::date parameter. A backfill script passed date_str = '2026-05-11' as a Postgres ::date parameter. Fix: convert with datetime.date.fromisoformat(date_str) before binding.

Case 2 — timestamptz column insert. A bulk insert script built rows from a DataFrame where the timestamp column held string values. Fix: pd.to_datetime(col).dt.to_pydatetime() to get proper datetime.datetime objects, then pass those to asyncpg.

Case 3 — interval arithmetic. A query computed a window with a Python timedelta passed as an interval parameter. This one failed silently until the WHERE clause produced zero rows. Fix: always pass typed datetime.timedelta objects, never formatted strings like '5 minutes'.

Triage checklist

When toordinal fires: scan the entire script for every parameter bound in an asyncpg execute(), fetch(), or executemany() call. Find all ::date, ::timestamptz, ::timestamp, and ::interval placeholders. For each, verify the Python type being passed: datetime.date, datetime.datetime, datetime.datetime, datetime.timedelta respectively.

The broader lesson: asyncpg is intentionally strict — it type-checks parameters against the Postgres column type before sending the query. This strictness is a feature (catches bugs early) but it punishes scripts written with Python's duck-typed string flexibility. The habit to build is: never pass date/time values as strings to asyncpg. Always construct the appropriate datetime type.

Chapter Eight

Recurring Pattern: Sub-agent vs OS-process Lifecycle

The agent's conversation ends. The process it spawned does not.

The Claude agent harness manages a conversation thread. When a sub-agent reaches the end of its task, the harness closes the thread and sends an "agent completed" notification. This is a signal about the conversation, not about any operating-system processes the agent's code may have started.

In this session that mismatch manifested repeatedly: a LoRA inference agent "completed" while the underlying python3 run_lora_inference.py process was still running on the GPU, consuming 8 GB of VRAM and writing output. Stopping the agent thread did nothing to the PID. Conversely, a separate data-load agent was still in its conversation thread while its spawned psql \COPY had already finished — because the agent was waiting for a user confirmation, not because the OS process was running.

Three implications

1. kill-style notifications sent to the agent do not propagate to spawned processes.
2. pgrep -f script_name.py is the ground truth for whether a long job is running.
3. Design long-running data jobs for idempotent restartability: upsert or INSERT ... ON CONFLICT DO NOTHING, checkpoint progress to a file or table, use date-range loops so a restart resumes from the last incomplete date.

The practical workflow that emerged: spawn the background process with a logfile redirect (python3 job.py > /tmp/job.log 2>&1 &), record the PID, and poll pgrep or tail /tmp/job.log to track real progress. The agent conversation can close, reopen, or be replaced entirely — the OS process persists through all of that.

Chapter Nine

Recurring Pattern: Parquet vs RDS Access Paths

Same data, two entirely different latency and freshness profiles — pick deliberately.

The system maintains two parallel paths to the analytical data: the production RDS instance reachable via an SSM port-forward tunnel, and a daily S3 parquet export queryable via DuckDB on the local machine. They contain the same underlying tables but with different trade-offs.

DimensionRDS via SSM tunnelS3 Parquet via DuckDB
Freshness Live / current state 1–2 days stale
Bulk read speed Slow (tunnel bottleneck) Fast (local columnar scan)
Auth overhead SSM session setup None after sync
JOIN across tables Native SQL, any join DuckDB SQL, file paths
Write operations Yes — inserts, updates Read-only snapshot

The parquet export is built by scripts/duckdb_parquet.py, runs nightly, and as of this session the latest export is 2026-05-18. The v9.2 clean cutoff — windows with window_ts ≥ 1778959500 — applies when filtering to post-launch data only.

For analytical queries — most ad-hoc work — prefer parquet. For freshness-critical reads like today's backfill state, you need RDS.

Decision heuristic from hub note #557

One additional nuance: for bulk reads that do need live data (e.g., dedup verification on a just-inserted backfill batch), the psql \COPY path through the tunnel still beats asyncpg for large result sets, as discussed in Chapter 6. The tunnel's weakness is asyncpg's wire-protocol overhead, not the tunnel itself.

Chapter Ten

The Two-Storage Durability Pattern

Hub notes live in git AND in Postgres. The combination survives session turnover, cross-device work, and full repo clones.

Every significant decision, experiment result, or architectural finding from a session should exist in two places before the session closes. The first is a docs/HUB_NOTE_*.md file committed to the repository — human-readable, version-controlled, diff-able, useful for code review context. The second is a row in public.notes on the production RDS — cross-session searchable by tag, never lost to a branch switch or git checkout.

This session produced 5 notes (IDs 557–561)

Note 557: Pipeline cache reality and the cache-key schema change. Note 558: XRP v9.2 deploy procedure and validation checklist. Note 559: v9.2.1 indicator trial plan and final verdict (SKIP). Note 560: v9.3 ETH trial plan, three paths, parallel agent design. Note 561: Five-stage pipeline explainer — the canonical training reference.

The dual-storage pattern solves a specific recurring problem: context loss between sessions. Without RDS notes, a future session that needs to understand "why did we reject the indicator trial?" must either read the git history (fragile — the relevant commit message may not name the trial explicitly) or re-run the experiment (wasteful). With RDS notes, the query is:

SQL — Hub note retrieval 
SELECT id, title, body
FROM public.notes
WHERE id IN (557, 558, 559, 560, 561)
ORDER BY id;

That query works from any machine with access to the RDS (via the SSM tunnel or the classifier-gpu port-forward), regardless of whether the git repository is available or on the correct branch.

Chapter Eleven

One-Sided Model Regression — When More Data Hurts Only One Direction

The v9.3 ETH retrain improved UP-side prediction consistently and regressed DOWN-side prediction consistently. The shape of the regression is a diagnostic fingerprint pointing at the cause.

The v9.3 ETH retrain doubled the training corpus (8.2 days → 18 days). The aggregate verdict was "SKIP" at the conservative production thresholds (p≥0.96 / p≤0.04), but the moderate-threshold sweep told a more interesting story. UP-side win-rate climbed by +0.5 to +4.3 percentage points at every threshold from 0.70 to 0.84. DOWN-side win-rate dropped by 2 to 6 points across the moderate range and only recovered to roughly flat at the extreme tail. More data made the model better in one direction and worse in the other — a result that demands explanation.

The diagnostic shape

Notice the curvature in the DOWN-side regression. It is largest where decision boundaries are softest (loose thresholds, p≤0.45) and shrinks toward zero where decision boundaries are sharpest (extreme tail, p≤0.21). The trial fires more DOWN calls than the baseline (889 versus 708 at p≤0.45) but at lower precision. This is the fingerprint of regime mismatch in the training corpus: older data contains DOWN-labeled windows whose features superficially resemble recent DOWN setups but whose price action played out differently. The model learns correlations that have since flipped or weakened, and applies them too eagerly to the held-out tail.

The DOWN-side regression is largest where decision boundaries are softest and shrinks toward zero where they are sharpest. The shape is diagnostic.

Why the UP side generalises and the DOWN side does not

UP and DOWN moves in crypto microstructure are not symmetric phenomena. UP moves tend to be driven by trend continuation, liquidity provision dynamics, and momentum signals that recur across volatility regimes. DOWN moves are more often driven by liquidation cascades, sentiment shocks, and regime-specific risk-off behaviour — patterns that are highly path-dependent on the macro context at the time. When the training window straddles a regime boundary, the model learns DOWN correlations from the older regime and over-applies them to the recent one. UP correlations, being more stable, suffer no equivalent penalty.

This is not unique to crypto. Equity volatility models routinely show the same shape: longer training windows help predicting normal-day returns but actively harm tail-event prediction. The mechanism is the same — tail dynamics are regime-specific.

Five things you can do about it

ApproachEffortLikely impact
Hybrid deployment — UP from v9.3, DOWN from v9.2Zero (engine config only)Recovers DOWN performance entirely; keeps UP win

The generalisable lesson

When more training data hurts performance, the shape of the regression tells you why. Pattern-match before you patch:

Shape of regressionLikely causeFix family
Uniform across all thresholdsOverfitting or label noiseRegularize harder, drop noisy rows
Worst at loose, recovers at tightRegime mismatch — old data has different dynamicsSample reweighting, recency cutoff, regime features
Worst at tight, OK at looseOld data has different tail behaviour (small-n confounding)More data of the same kind, or accept undertrained tail
One direction degraded, other improvedAsymmetric regime mismatch (microstructure shifts differently for UP/DOWN)Hybrid deployment, asymmetric windows, direction-specific models

The v9.3 ETH result is a case of the fourth row plus the second row — both effects compound because UP and DOWN are semi-independent processes being trained as a single binary classifier. The pragmatic answer is the hybrid deployment, which acknowledges that the production engine already supports running multiple strategies against the same model emissions. The principled answer is asymmetric training windows, which requires production scoring path changes but eliminates the compromise.

Methods. Win-rate confidence intervals use the Wilson score method (z = 1.96 for 95%), which remains well-calibrated even for proportions near 0 or 1 and small sample sizes. Cross-model comparison uses a two-proportion z-test with pooled variance: z = (WRtrial − WRbaseline) / SE, where SE = √[p̄(1−p̄)(1/nb + 1/nt)] and p̄ is the combined win rate; p-values are two-sided (α = 0.05, marked ★). Bootstrap 95% CIs on the WR delta use 10,000 independent resamples of both populations with a fixed seed (42) for reproducibility; reported as empirical percentile intervals. The Sharpe-equivalent is computed as (mean per-fire P&L / std per-fire P&L) × √n, tested against zero via a one-sample t-test: t = mean × √n / std, two-sided. All P&L simulations assume even-money binary outcome ($5 win / $5 loss) sorted by window_ts across the single held-out day (2026-05-17 UTC).

Chapter Twelve

Hyperparameter Search With Optuna — Letting The Computer Pick The Numbers

When defaults are someone else's choices and you have spare compute, asking a search algorithm to choose your hyperparameters is almost always worth it. Two hundred trials, eight parameters, one clear signal.

Every machine-learning model has knobs the practitioner picks before training begins — the depth of trees, the speed of learning, the strength of regularisation. Pick badly and the model under-fits or over-fits. Pick well and you squeeze out the last few percentage points of accuracy that often separate a deployed model from one that gets archived. The v9.2 family was tuned for BTC's data distribution, and when we trained v9.3 ETH on the larger 18-day corpus, we kept those same defaults. Optuna let us ask: what does ETH actually want?

What Optuna is

Optuna is a hyperparameter-search framework. You define an objective function that takes hyperparameters and returns a number (lower or higher is better). Optuna then chooses successive hyperparameter combinations to evaluate, using prior trial results to focus the search on promising regions. Two pieces matter most for our purposes.

The sampler is the algorithm that picks the next set of hyperparameters. Optuna's default is the Tree-structured Parzen Estimator (TPE), which models the distribution of "good" and "bad" hyperparameter values seen so far and samples preferentially from the good region. It is dramatically better than random search at high-dimensional discovery and almost always better than grid search.

The pruner is the algorithm that abandons unpromising trials early. With LightGBM, that means stopping a trial after just a few boosting rounds if the intermediate validation loss is worse than the median of trials at the same step. We used MedianPruner, which killed roughly the bottom half of trials before they finished training all 500 boosting rounds — recovering wall-clock time we then spent on more search.

Why search beats defaults — even sensible defaults

LightGBM's defaults are sensible. The v9.2 V5_LGB_PARAMS were tuned on BTC data months earlier. But "sensible" is an average over many problems. The right hyperparameters for THIS dataset, with THIS feature set, at THIS corpus size, are not the same as the ones for BTC at the previous corpus. Search exploits the specifics.

The objective and search budget

We optimised dev log-loss summed across all six per-Δ heads. Log-loss is a natural choice because it penalises confident wrong predictions more than unconfident ones, which aligns well with how trading strategies use the model's probability output. We split the trial training corpus three ways: 16 days for the per-trial training set, 2 days held back as dev for the Optuna objective, and the original 1 day of held-out test untouched (only used after the search picked a winner). This three-way split prevents Optuna from over-fitting to the dev set and ruining downstream evaluation.

The search budget was 200 trials with 8 parallel workers (chosen as a sweet spot between throughput and SQLite contention). On the dev box's 16-core CPU, with OMP threading patched to single-thread per worker, 200 trials completed in roughly four minutes. By comparison, the same search at default thread settings would have taken about thirty minutes — an interaction between Optuna's thread workers and LightGBM's internal threading produced GIL contention that wasted nearly all cores. The fix was a single environment variable.

What the result is telling us about over-fitting

The signal here is unambiguous. Optuna selected for a simpler, more regularised model than the defaults: shallower trees (max_depth 12 → 7), larger leaves (min_data_in_leaf 100 → 225), slower learning rate (0.05 → 0.017), row subsampling (1.0 → 0.70), and L2 weight decay (0.0 → 0.79). Each of these moves the model away from memorising the training corpus and toward generalising the patterns in it.

Why? The v9.3 ETH corpus is small. Eighteen days of five-minute windows is roughly 5,400 windows. With six per-Δ buckets each getting their own model, each per-Δ booster sees only about 900 training examples. A model with depth 12 and 63 leaves has on the order of 2^12 potential leaf paths — more degrees of freedom than the data can constrain. The default architecture, tuned for BTC's larger corpus, is over-parameterised here. Optuna's regularisation choices are saying: with this little data, simpler is better.

The under-fitting / over-fitting / right-fitting distinction

An under-fit model has too few degrees of freedom to capture the patterns in the training data — its training-set error is high. An over-fit model has too many degrees of freedom and memorises noise specific to the training set — its training-set error is very low but its held-out error is high. A right-fit model has enough flexibility to capture the patterns and enough constraints to ignore the noise. Hyperparameter search is the process of finding right-fit by exploring the over-fit / under-fit boundary empirically.

The DOWN side is the more important reading. The Optuna model does not fix the regime-mismatch regression that Chapter Eleven diagnosed. At loose-to-moderate DOWN thresholds (p≤0.45 through p≤0.33) the Optuna model still loses to baseline by 1.1 to 6.0 percentage points — almost identically to the default v9.3. The diagnostic conclusion from Chapter Eleven is reinforced

Hyperparameter search cannot fix data-level problems. If the older training data contains DOWN-labeled windows whose features resolved differently in the older regime, no choice of num_leaves or lambda_l2 reaches into the training set and silences those rows. The Optuna model fires fewer low-confidence DOWN calls than the default v9.3 (n=852 vs 887 at p≤0.45) because the regularisation has flattened the prediction distribution. But the predictions it still makes are no more correct than the default model's — confirming the issue is informational, not structural. The right family of fix is data-level: sample reweighting, recency cutoff, asymmetric training windows from Ch11's option list.

What changed in our deployment thinking

The Optuna result does not by itself decide whether to deploy v9.3 ETH. A 1.2% reduction in dev log-loss is meaningful but not transformative. What it does is tell us that the v9.3 model with tuned hyperparameters is a different beast than the v9.3 model with defaults — more regularised, less aggressive, more likely to generalise. The held-out evaluation that follows the search uses these tuned parameters, and only that evaluation determines whether v9.3-Optuna meaningfully beats baseline at our trading thresholds.

The broader lesson: hyperparameter search is cheap, especially with caching of the data pipeline. Once the corpus and held-out features are stable on disk, running 200 trials takes the time of a coffee break. Skipping the search to save four minutes when training a new model is almost always the wrong trade — and the over-/under-fitting signal Optuna reveals through its parameter-importance ranking is itself worth the run, independent of the final best-value.
