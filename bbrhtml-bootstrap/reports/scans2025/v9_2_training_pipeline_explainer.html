v9.2 — How We Build, Train, Test, Calibrate

The 5-stage canonical training pipeline: from raw signal_evaluations rows to a calibrated production scorer that returns a trustworthy probability.
📅 2026-05-20 Author: claude-session Cross-ref: training.build_dataset + training.train_lgb_v5 (canonical entrypoints)
SLIDE 1 / 5
STAGE 1 · BUILD

Assemble the training corpus

Take per-tick features from signal_evaluations and join them to per-window outcomes from market_data. One row per (asset, window_ts, seconds_to_close) → (78 features + 1 label).

Features come from the live scorer's snapshot at score time. Labels come from the resolved Polymarket outcome at window close. The join is the source of truth.

Why this join shape

  • features → signal_evaluations: same source as live serving → train/serve skew = 0
  • labels → market_data: resolved outcomes that we can't see at score time → no look-ahead
  • Filter window_ts > cutoff (e.g. ≥ 1778959500) to skip pre-fix contaminated periods

Code entry point

training.build_dataset — the canonical builder. Per feedback_canonical_training.md, all other paths are anti-patterns.

Output: pandas DataFrame ready for train_lgb_v5.

SLIDE 2 / 5
STAGE 2 · TRAIN

Six per-Δ LightGBM heads

Instead of one booster trying to learn how predictions decay with seconds-to-close, we train SIX boosters — one per Δ bucket. Each sees only rows from its bucket.

Each of the 6 boosters specializes in its window-position range. A 5m window is ~300 seconds, so all of stc ∈ [0, 300] is covered by the 6 buckets.

Hyperparameters (LightGBM)

  • num_leaves = 63
  • learning_rate = 0.05
  • num_boost_round = 500
  • early_stopping_rounds = 50 on dev
  • min_data_in_leaf = 100
  • objective: binary, metric: binary_logloss

Why per-Δ vs one shared booster

Feature importance shifts dramatically with seconds-to-close. Far from close: tfm_* forecasts dominate. Near close: vpin + recent price ret dominates. One shared booster averages those signals; per-Δ heads learn each regime independently.

SLIDE 3 / 5
STAGE 3 · TEST

Held-out evaluation

Predict on the 2-day test tail (never seen during training or hyperparameter selection). Measure log-loss, accuracy, and win-rate at conservative thresholds. This is the only number we trust.

The "conservative threshold" choice is where on this curve to operate. v9.2 BTC LIVE lives at p ≤ 0.04 (DOWN) and p ≥ 0.96 (UP) — high WR, low volume.

Held-out metrics — what we report

  • Log-loss: average −log(p_correct). Measures full distribution quality.
  • Accuracy: argmax correct rate. Coarse-grained.
  • WR @ threshold: precision at the operating point we actually trade at.
  • Fires/day @ threshold: volume sanity check — need enough fires to be statistically real.

What we never use

  • WR on the training set (overfitting illusion)
  • WR on dev only (already used for hyperparameter selection — biased)
  • Numbers from p ≥ 0.5 split (trades happen at thresholds, not at 0.5)

SLIDE 4 / 5
STAGE 4 · ECE

Expected Calibration Error — "do the numbers mean what they say?"

A model can have great accuracy and still emit nonsense probabilities. ECE asks: when the model says p = 0.9, does it actually win 90% of the time?

The raw LightGBM model is well-trained but its probabilities don't line up with reality. ECE quantifies the gap. Lower ECE = more trustworthy probabilities.

Why this matters for trading

Sizing strategies use p directly: Kelly fraction = (p·b − q)/b. If p is overstated, you bet too much and blow up. If it's understated, you leave EV on the table. Calibration is the bridge between model output and rational position size.

What good ECE looks like

  • ECE < 0.01: excellent (within sampling noise of perfect)
  • ECE 0.01–0.03: production-acceptable
  • ECE 0.03–0.05: serviceable but worth calibrating
  • ECE > 0.05: don't trust the probabilities; fix calibration before trading sizing on them

STAGE 5 · ISO

Isotonic calibration — the post-hoc fix

Don't retrain the model to fix calibration — that risks regressing accuracy. Instead, fit a monotonic function f that maps raw output to calibrated output. Apply after the model, at serve time.

    • monotone non-decreasing: higher raw p → higher cal p • range [0, 1]: clipped output • f(0) = 0, f(1) = 1: endpoints preserved • piecewise-linear: simple + serialisable
Six iso calibrators in v9.2 One iso per per-Δ booster head. Same fit recipe, independent curves — booster_30 may have totally different miscalibration shape than booster_240. At serve time stc → pick booster → predict raw_p → apply iso → emit calibrated probability_lgb_v9_2(_eth/xrp)
The green curve is the iso calibrator. Reading it: raw 0.95 → calibrated 0.89. The curve "bends" the identity diagonal to match where the empirical WR points actually fell in slide 4.

Why iso vs Platt scaling vs temperature

  • iso: flexible (any monotone shape), no parametric assumption — wins on complex miscalibration patterns ✓
  • Platt (sigmoid): 2 parameters, assumes a logistic shape. Cheaper but less flexible.
  • Temperature: 1 parameter, just rescales logits. Doesn't fix shape issues.

Iso is the right default. We use it across v9.2 BTC / ETH / XRP.

Where iso lives in the codebase

  • Fit: training/calibration_posthoc/fit_isotonic.py
  • Apply at serve: app/isotonic_calibrator.py
  • S3 layout: calibration/isotonic_v9_2/v<n>/isotonic.pkl
  • Gated by env flag: ISOTONIC_CALIBRATION_V9_2_ENABLED
RECAP

The 5 stages, in one sentence each

  1. BUILD — Join per-tick features from signal_evaluations with per-window outcomes from market_data to get the (78 features + label) dataset.
  2. TRAIN — Fit six LightGBM boosters, one per Δ bucket, with 14d/3d/2d time-ordered train/dev/test split.
  3. TEST — Predict on held-out tail; measure log-loss, accuracy, and WR at conservative thresholds (e.g. p ≤ 0.04 DOWN).
  4. ECE — Bin predictions, compare to empirical win-rates; quantify the gap between predicted probability and reality.
  5. ISO — Fit a monotone non-decreasing function on dev to map raw → calibrated; apply at serve time per Δ bucket.
