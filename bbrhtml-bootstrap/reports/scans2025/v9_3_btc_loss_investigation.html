For this investigation we pulled all 58 windows with at least one v9.3 BTC emission and joined to market_data on window_ts. 56 resolved (30 UP / 26 DOWN); 2 unresolved. Per-window dedup: we report max emitted probability per window (for UP-side fire decisions) and min (for DOWN-side fire decisions). This matches how the engine would consume the signal — first crossing of the threshold within the window triggers the decision.

A loss is defined as: any window where v9.3 BTC crossed the UP threshold and the market resolved DOWN, OR crossed the DOWN threshold and resolved UP. Same-side wins (UP fire → UP outcome) and opposing-side wins (DOWN fire → DOWN outcome) are wins. close_price=0 in market_data so we cannot show price-move overlays in this report; outcomes are honest because they come from Polymarket resolution.

6. Can v9.3 work as a filter on v9.2?

v9.2 BTC alone at p≥0.72 hits 14/16 = 87.5% UP WR in this 5h window. If we require BOTH models to fire (v9.2 ≥ 0.72 AND v9.3 ≥ 0.72), we get 6/6 = 100% UP WR — a clean filter, but n=6 fires in 5 hours is a low-throughput signal. No v9.2 UP fire had v9.3 max below 0.5 (i.e. v9.3 never strongly disagrees with v9.2 UP), so v9.3 cannot be a strong-veto filter at all — it can only be a same-direction confirm filter.

Filter mode: v9.3 as confirm signal on v9.2 UP @ 0.72

Confirm (both ≥ 0.72): 6 fires / 6 wins / 100% WR.
v9.2-only (v9.3 disagrees by going below 0.72): 10 fires / 8 wins / 80% WR.
Filtering loses 10 of 16 fires (62% throughput reduction) but the gained precision is genuine — 6/6 is not yet statistically meaningful (Wilson LB 0.61) but if it holds over 24-48h more data it would be a candidate filter signal. That is the only honest "win" we can find for v9.3 BTC.

7. The headline question

Is there ANY winning operating point we missed? No — not as a standalone model. The 0.005-step sweep across UP [0.50, 0.80] and DOWN [0.20, 0.50] covers every plausible cutpoint. At every cutpoint where v9.3 BTC fires with n ≥ 10 windows, v9.2 BTC at the same threshold on the same hours produces a higher WR. The model is structurally dominated by the LIVE baseline.

The only candidate "win" is filter mode — v9.3 confirming v9.2 UP fires lifts WR from 87.5% (14/16) to 100% (6/6). This is potentially actionable but requires more data (n=6 is small). It will not be visible at the planned tight thresholds (0.935/0.065) because v9.3 BTC's compressed output never reaches them.

8. Recommendation

What to do

1. Keep v9_3_btc_raw_lgb and v9_3_btc_tight in GHOST. Do not promote. The tight variant never fires; the raw variant is dominated by LIVE v9.2 BTC.

2. Do NOT spend more cycles retuning v9.3 BTC's threshold. The 0.005-step sweep is exhaustive and the answer is "no cutpoint works as a standalone signal".

3. Track the filter-mode hypothesis. Add a derived signal v9_2_AND_v9_3_btc_confirm in GHOST and let it accumulate fires for 24-48h. If it holds ≥90% WR with n ≥ 20, it becomes a candidate stack.

4. Address the upstream cause of v9.3's compressed output range — 15 features are NaN-filled at training and serve time (binance_depth_*, clob_pre_*, vpin_60s_*, nested_5m_oi_delta_cumulative, gamma_*). A retrain without those columns (or with their NaN policy fixed) is the right next step if we still want v9.3 BTC at all.

5. Don't worry: v9.2 BTC is doing its job. 17/21 (81.0%) at LIVE thresholds in this 5h window. The GHOST mining was useful — it told us the new model isn't ready, before it could lose any real money.
