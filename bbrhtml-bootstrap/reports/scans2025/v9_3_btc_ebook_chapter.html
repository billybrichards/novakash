01 · Trigger

A few extra losses.

BTC has been running v9.2 LIVE for weeks. The thresholds are sharp on purpose — UP fires at p ≥ 0.72, DOWN at p ≤ 0.20. Wins disappear into Polymarket's autoredeem and never hit the trades table. Losses do. That asymmetry hides the strategy's true win rate, but it also means: when a few extra losses show up, you notice immediately.

On 2026-05-18 we shipped iso_expand — same UP/DOWN thresholds, but a post_iso probability behind it, claiming +44% volume and a +1.6 pp WR. For a couple of days the volume came in clean. Then a handful of losses landed in a row. Not a regime break, not a model drift event — just enough noise to make a person ask the question that starts every retrain.

Can we just improve it? Billy — 2026-05-22, around the time the corpus was queued

That sentence is the trigger for this chapter. The rest of it is the answer: a hybrid data pipe, a walk-forward CV that quietly demoted the old baseline, a feature gap that turned out to be a +7 pp leak, a reweight experiment that looked obvious and wasn't, and a meta-stack that finally cracked the DOWN side.

02 · Infra

The DuckDB unlock.

Before any model can be trained, the data has to land. On a small training corpus that is a non-issue; on the BTC corpus — tens of thousands of windows, hundreds of features, tick-level OOF data — it became the bottleneck that gated the entire afternoon.

The first attempt followed the path of least resistance: SSM port-forward into RDS, asyncpg connection, one big SELECT. Familiar. Reliable in the small. And catastrophic at scale: thirteen minutes of hung tunnel before the query timed out, no rows returned. The classifier-gpu jump host was healthy; RDS was responsive on small queries. The pathology was the combination of asyncpg's buffer behaviour on large result sets with a tunneled TCP stream where backpressure gets ambiguous. Hard-stall. Not crash, not progress — a quiet sit.

The fix flipped the model. Instead of streaming a huge result set through a fragile tunnel, pull most of the corpus from the daily S3 parquet export and pull only the delta — rows newer than the export cutoff — through SSM. DuckDB reads S3 parquet natively, in parallel, with predicate pushdown. The bulk pull dropped from > 10 minutes hanging to 69 seconds for 32.4 MB.

Fig. 1 · Hybrid bulk + delta ingest

Why asyncpg stalled

The tunneled TCP stream between the local box and RDS goes through SSM session manager + a port-forward on classifier-gpu. That path is fine for paginated reads and small bursty queries. Under a single large SELECT with no statement cursor, asyncpg buffers aggressively, the kernel slows the tunnel, and the whole flow enters a polite stall: no error, no progress.

The fix is not to "tune asyncpg" — it is to not put the bulk on the tunnel. The daily RDS-to-S3 parquet export (Reference: DuckDB Parquet access, scripts/duckdb_parquet.py) already gives a clean snapshot with partitioned cutoffs. The tunnel only carries the small delta that lives between the snapshot and now.

The hybrid pattern

  • bulk · S3 parquet via DuckDB btc_bulk_FULL_2026_05_18.parquet (32.4 MB on disk). DuckDB reads it with predicate pushdown, projects only the columns we need, takes 69 s end-to-end on this box.
  • delta · RDS via SSM + asyncpg Only rows with window_ts > export_cutoff. A few thousand rows over a few hours. Asyncpg is fine here because the result set is small.
  • merge · pandas.concat Same schema both sides, dedupe on (asset_id, window_ts, delta_pct), sort. The combined corpus lands at btc_corpus_combined.parquet.
  • cache · /tmp/btc_v9_3_cache/ Every intermediate parquet stays on disk. Re-running an ablation does not re-pull. The whole afternoon's experiments share a single bulk fetch.

The pull, in code

# /tmp/btc_v9_3_cache is canonical for this run
import duckdb, pandas as pd
from pathlib import Path

CACHE = Path("/tmp/btc_v9_3_cache")
EXPORT_TS = 1779408000   # 2026-05-18 export cutoff

# 1) bulk · S3 parquet, ~32 MB, 69s
duckdb.sql(f"""
  COPY (
    SELECT *
    FROM read_parquet('s3://novakash-rds-exports/.../ticks_v3_composite/*.parquet')
    WHERE asset_id = 'btc' AND window_ts <= {EXPORT_TS}
  ) TO '{CACHE}/btc_bulk_FULL_2026_05_18.parquet' (FORMAT PARQUET);
""")

# 2) delta · RDS via SSM port-forward, <5s for a few hours
async with asyncpg.create_pool(dsn=PG_LOCAL_TUNNEL) as pool:
    rows = await pool.fetch(
        "SELECT * FROM ticks_v3_composite "
        "WHERE asset_id='btc' AND window_ts > $1",
        EXPORT_TS,
    )
delta = pd.DataFrame(rows, columns=COLS)

# 3) merge
bulk = pd.read_parquet(CACHE / "btc_bulk_FULL_2026_05_18.parquet")
combined = (
    pd.concat([bulk, delta], ignore_index=True)
      .drop_duplicates(["asset_id", "window_ts", "delta_pct"])
      .sort_values(["window_ts", "delta_pct"])
      .reset_index(drop=True)
)
combined.to_parquet(CACHE / "btc_corpus_combined.parquet")
Why this matters past today

This is now the canonical pattern for "I need the full corpus on the local box". S3 parquet bulk + SSM delta, both cached, asyncpg never asked to carry more than a handful of hours. It generalises to ETH and XRP without a rewrite.

03 · Honesty

The walk-forward demotion.

The first thing we learned, before any new feature, was that the v9.2 single-day held-out test had been flattering itself. Not by a tiny amount — by almost four points at the extreme threshold.

The original v9.2 sweep on BTC reported 95.0% WR at UP 0.96 over 161 windows — a single day's held-out slice. Honest, but lucky. When we re-ran the same baseline LightGBM under a 20-fold rolling walk-forward across the same corpus, the UP-0.96 cell drops to 91.3% over 1,488 windows. Same architecture, same features, same hyperparams. Different lens.

The single-day test is a lottery. The walk-forward is what the strategy actually faces, averaged over twenty different market days, each with its own regime. The 1,488-window count is honest precisely because it reflects how often the threshold actually fires; the 161 was always the day's tail.

Lesson

Every claim about "X% at threshold T" should specify the CV scheme. Single-day held-out is a useful debugging tool. It is a misleading shipping claim. From this chapter onwards every BTC number here is walk-forward unless explicitly flagged otherwise.

04 · Discovery

Eight NaN-filled features.

The walk-forward run revealed an awkward fact: of the 78 features the BTC trainer expected, eight were arriving as NaN-fill across the entire bulk. Either the join had quietly drifted, or those features had always been missing and nobody had checked.

The eight, in the order they came back to life:

  • tfm_tail_risk TimesFM quantile-derived tail measure. Sourced from ticks_timesfm. Stale-tolerant via ASOF.
  • tfm_skew Quantile asymmetry. Same source. ASOF-joined.
  • tfm_spread_norm Normalised forecast spread. Same source. ASOF-joined.
  • tfm_quantile_ratio Upper-to-lower quantile ratio. Same source. ASOF-joined.
  • v3_elm Composite extreme-liquidity metric from ticks_v3_composite. ASOF-joined back to the tick stream.
  • regime_num Pandas map of the regime string column to a stable integer ID. Was just missing wiring.
  • delta_source_num Same pattern — categorical mapping that lived in the production engine but never made it into the offline training corpus.
  • delta_pct_log_safe Sign-preserving log-magnitude of delta_pct. A computed feature whose recipe lived only in the engine.

Filling them was the obvious first move. Pandas, no new data sources: 

# ASOF-join TFM + v3 features onto the corpus
tfm = pd.read_parquet(CACHE / "btc_ticks_timesfm.parquet") \
        .sort_values("event_ts")
v3  = pd.read_parquet(CACHE / "btc_ticks_v3_composite.parquet") \
        .sort_values("event_ts")

corpus = corpus.sort_values("event_ts")

corpus = pd.merge_asof(
    corpus, tfm[["event_ts", "tfm_tail_risk", "tfm_skew",
                  "tfm_spread_norm", "tfm_quantile_ratio"]],
    on="event_ts", direction="backward",
    tolerance=pd.Timedelta(seconds=30),
)
corpus = pd.merge_asof(
    corpus, v3[["event_ts", "v3_elm"]],
    on="event_ts", direction="backward",
    tolerance=pd.Timedelta(seconds=30),
)

# cheap categorical maps
corpus["regime_num"] = corpus["regime"].map(REGIME_TO_INT).fillna(-1)
corpus["delta_source_num"] = corpus["delta_source"].map(SRC_TO_INT).fillna(-1)
corpus["delta_pct_log_safe"] = np.sign(corpus.delta_pct) * np.log1p(corpus.delta_pct.abs())

The expectation was an obvious win. Eight features going from "noise" to "real signal" should move the needle. What actually happened was the first counter-intuitive result of the day.

Counter-intuitive · the fill alone hurt

At LIVE thresholds, the gap-fixed baseline was worse than the NaN-filled one. UP 0.72 slipped about −1.4 pp; DOWN 0.20 slipped about −2.4 pp. Stale ASOF-joined features — the TFM stream lags the tick stream and the 30 s tolerance is wider than ideal — were giving the model almost-right values that it then over-trusted.

This is the well-known "missing-data-as-information" trap: when something has been NaN-filled across the entire corpus, LightGBM has implicitly learned to ignore it. Hand it a real-but-stale value and you do not get the signal you wanted; you get a confidently wrong feature.

That negative result reframed the problem. The 78-feature base was not missing eight features; it was missing useful ones. The next step was to add value without reaching for noisy external joins.

05 · Enrichment

Tier 1 + 2 + 3 — +7.2 pp in pure pandas.

The breakthrough turned out to be entirely derived. No new joins, no new data sources — just three tiers of feature engineering on top of the existing base, stacked in order of how much they assume about per-window context.

01

Rename for the trainer

Three columns in the v3 composite stream are present but under names the trainer's feature list doesn't recognise. A rename costs zero CPU and reconnects three real signals.

  • v3_cascade_signal → v3_cascade
  • v3_taker_signal → v3_taker
  • v3_momentum_signal → v3_momentum

02

Pure-row derivations

Per-row transforms with no aggregation. Cheap, deterministic, and they expose relationships the model would otherwise have to learn from scratch.

  • v2_logit = log(p / (1-p))
  • session_bucket ∈ {asia, eu, us, weekend}
  • hour_of_day (0–23)
  • minute_of_hour (0–59)
  • source_delta_divergence
Cumulative lift · +1 to +2 pp
03

Per-window groupby

The real lift. For each (asset_id, window_ts, delta_pct) group, aggregate the tick stream into six summary features that capture the shape of the window, not just its head.

  • nested_5m_avg_prob_up
  • nested_5m_prob_trend · regression slope
  • nested_5m_gate_pass_rate
  • nested_5m_regime_consistent
  • nested_5m_vpin_peak
  • nested_5m_n_obs
Most of the lift · +5 to +7 pp

Why Tier 3 carried it

The base 78-feature representation treats every tick mostly in isolation. A window has a distribution: how the per-tick probability moves, whether the gate accepts most ticks or flips frequently, whether the regime label is stable across the window, where the VPIN peak lands. Those quantities are not difficult to compute — they take one groupby — but the model has no way to invent them from a single tick. 

# Tier 3 · per-window aggregates
from scipy.stats import linregress

def _trend(p):
    if p.size < 3: return 0.0
    x = np.arange(p.size, dtype=np.float64)
    s = linregress(x, p.values).slope
    return 0.0 if np.isnan(s) else s

agg = corpus.groupby(["asset_id", "window_ts", "delta_pct"]).agg(
    nested_5m_avg_prob_up    = ("probability_up", "mean"),
    nested_5m_prob_trend     = ("probability_up", _trend),
    nested_5m_gate_pass_rate = ("gate_pass", "mean"),
    nested_5m_regime_consistent = ("regime_num",
                                  lambda r: (r == r.mode().iat[0]).mean()),
    nested_5m_vpin_peak      = ("vpin", "max"),
    nested_5m_n_obs          = ("event_ts", "count"),
).reset_index()

corpus = corpus.merge(
    agg, on=["asset_id", "window_ts", "delta_pct"], how="left",
)

The uncomfortable implication

If +7.2 pp at UP 0.72 sits behind a half-day of pure-pandas feature engineering, then production v9.2 BTC is almost certainly running with the same feature gaps that the offline baseline had. The nested_5m_* family alone — six features — carried most of the lift in the ablation. They do not exist in the live tick stream today.

Action

The ENRICHED corpus is the cheapest, safest improvement in this report. Re-computing six groupby aggregates per window is a few hundred microseconds of pandas. The deploy work is real — the engine has to learn to emit nested_5m_* at tick time — but the modelling work is done.

06 · A trap

Reweight: not a free win.

The v9.4 ETH chapter ended on a clean note: down-side reweighting tilted the loss towards the asymmetric DOWN cell and the ETH gate went up. Trying the same trick on BTC was the obvious next move. It is not a free win.

The setup is identical to the ETH version. The training objective for each per-Δ head is binary logloss; we multiply the loss on DOWN-labelled rows by a constant k. For k = 3 — the value that worked on ETH — the BTC pattern is:

v9.3 ENRICHED · no-reweight vs DOWN reweight ×3 · LIVE-region thresholds
Cell norw window WR rw3 window WR Δ (pp) verdict
UP 0.72 76.87% 73.87% −3.00 UP hurt
UP 0.80 83.23% 80.04% −3.19 UP hurt
UP 0.96 91.64% 91.17% −0.47 UP hurt
DOWN 0.12 87.92% 84.92% −3.00 DOWN hurt
DOWN 0.16 83.57% 82.74% −0.83 DOWN hurt
DOWN 0.20 79.88% 80.67% +0.79 DOWN helped

The clean ETH story does not replicate on BTC. Down-reweighting helps the DOWN side in a narrow band — roughly p ≤ 0.20 — but at most by a couple of points, and it hurts the UP side across the entire threshold range. At UP 0.72 the model gives up three points; at UP 0.80 another three.

Why the asymmetry differs from ETH

The intuition is simple if a little uncomfortable: the model has a fixed budget. Each per-Δ head is a 63-leaf LightGBM with a finite number of effective splits. When you tell it to care more about DOWN, it spends more of its capacity on the DOWN tail — which on BTC is already well-served by the base distribution. The marginal lift on DOWN is small, and the cost to UP, which sits in a much busier part of the distribution, is large.

On ETH the same trick worked because the base model under-served the DOWN tail significantly. On BTC, the v9.2 base — and now the ENRICHED base — already calibrates the DOWN side well. There is little to gain by paying for it twice.

Decision

Drop down-reweighting from the BTC v9.3 candidate. The ENRICHED no-reweight model is the production candidate. Reweighting stays in the ETH recipe where it earns its keep.

What this confirms

Asset-specific. Per-asset ablation is not optional. The instinct to copy a winning trick across assets is almost always wrong: BTC and ETH have measurably different base-rate calibrations, and the same loss-weighting recipe lands on opposite sides of the trade-off.

07 · Breakthrough

Meta-features — the DOWN-side crack.

Of every experiment in this chapter, this is the one with the biggest single number and the biggest single caveat. +11.6 pp at DOWN 0.20. And a train-serve skew that means it does not deploy without an engine refactor.

The idea: instead of training a single head on 78 features, train a two-stage model. Stage A is the ENRICHED model, exactly as above — producing one probability per tick. From its walk-forward folds we already have out-of-fold per-tick predictions for the entire corpus, which is the magic ingredient: an OOF probability for every tick that the Stage B model is allowed to use as input without data leakage, because each tick's prediction comes from a model that never saw that tick.

Stage B then summarises the OOF prediction trajectory for each window into six meta-features:

  • p50_crossings — count of sign changes around the 0.5 line. A "decisive" window has zero; a "noisy" window has many.
  • p_std — standard deviation of the OOF probability across ticks in the window.
  • p_trend — regression slope of the OOF probability against tick index. Conviction building or eroding?
  • p_last — the OOF probability at the final tick.
  • p_max — maximum OOF probability observed in the window.
  • p_min — minimum.

These six features get appended to the 78 base, the per-Δ heads are re-trained on 84 features, and each fold's training data uses meta-features derived from earlier folds' OOF only — no leakage forward.

Fig. 2 · Two-stage meta architecture

The math, in one place

# Stage A · already trained as the ENRICHED walk-forward run
#   → oof[i] = ENRICHED model's prediction for tick i, from the fold
#     that did NOT contain tick i in its training set
oof = pd.read_parquet(CACHE / "btc_oof_predictions.parquet")

# Stage A → meta features (per window)
def _crossings(p):
    return int(np.sum(np.diff((p > 0.5).astype(int)) != 0))

def _trend(p):
    if p.size < 3: return 0.0
    s = linregress(np.arange(p.size), p.values).slope
    return 0.0 if np.isnan(s) else s

meta = oof.groupby(["asset_id", "window_ts", "delta_pct"]).agg(
    p50_crossings = ("prob_up_oof", _crossings),
    p_std         = ("prob_up_oof", "std"),
    p_trend       = ("prob_up_oof", _trend),
    p_last        = ("prob_up_oof", "last"),
    p_max         = ("prob_up_oof", "max"),
    p_min         = ("prob_up_oof", "min"),
).reset_index()

meta.to_parquet(CACHE / "btc_meta_features.parquet")

# Stage B · re-train on 78 base + 6 meta = 84 features
# Critical: for each fold k, the meta features used in training
# are computed ONLY from folds 0..k-1 OOF. No same-fold contamination.

What the meta-features actually encode

  • p50_crossings — encodes confusion. A window where Stage A flips back and forth over 0.5 is exactly the regime Stage B should down-weight on DOWN entries.
  • p_trend — encodes conviction build. A positive slope on the OOF probability across the window correlates with the true outcome more reliably than the final probability alone.
  • p_last - p_min / p_max - p_last — together a poor-man's window shape feature. Stage B learns to use them as a soft confirmation.
  • p_std — pure noise band. Wide-stdev windows are the ones where Stage A is least reliable; Stage B uses this as a "trust myself less" signal.

The train-serve caveat · don't ship it yet

The engine doesn't compute meta-features per tick today. The offline pipeline cheated — it had access to the entire window's worth of ticks before producing a Stage A probability sequence to summarise.

Production cannot do that. By the time the engine has a decision to make, it has seen part of the window, not all of it. To deploy v9.3 META we need the engine to maintain a per-window rolling OOF buffer, score Stage A on every tick, recompute the six meta-features on each tick using only the ticks observed so far, and feed Stage B. That is the same pattern v9.5 ETH uses and the same engine refactor is the prerequisite for shipping META on BTC.

08 · In flight

The SUPER-ENRICHED experiment.

Everything above produced clean, reportable numbers by 21:11. The SUPER-ENRICHED run is still in flight as this chapter is being written. It tests the next obvious question: what if Stage B got the predictions of every other prior model too?

The base 78 + 6 meta = 84 features. SUPER-ENRICHED adds another sixteen on top:

The six prior-model probabilities

  • probability_lgb_v9_1 — the previous-generation LGB direct prediction.
  • probability_lgb_v9_2 — the model that is in production today, used here as a feature.
  • probability_lgb_v12 — the longer-context v12 head.
  • probability_v2_meta_gate — the legacy meta-gate at v2.
  • probability_v9_2_meta_gate — the v9.2 meta-gate.
  • probability_v12_meta_gate — the v12 meta-gate.

The ensemble stats

For the three LGB direct predictions — v9_1, v9_2, v12 — compute the mean, std, max, min, and range across the trio. That is four ensemble summary features. Add log-odds transforms of the three LGB probabilities (so the model has access to both probability and logit scales). Total bonus feature count: sixteen. 

# Bonus block · prior model probabilities + ensemble stats
priors = [
    "probability_lgb_v9_1",
    "probability_lgb_v9_2",
    "probability_lgb_v12",
    "probability_v2_meta_gate",
    "probability_v9_2_meta_gate",
    "probability_v12_meta_gate",
]

corpus[priors] = corpus[priors].astype(np.float32).fillna(0.5)

# ensemble stats across the three LGB direct predictions
lgb_cols = ["probability_lgb_v9_1", "probability_lgb_v9_2", "probability_lgb_v12"]
lgb_mat = corpus[lgb_cols].values
corpus["ens_lgb_mean"]  = lgb_mat.mean(axis=1)
corpus["ens_lgb_std"]   = lgb_mat.std (axis=1)
corpus["ens_lgb_max"]   = lgb_mat.max (axis=1)
corpus["ens_lgb_min"]   = lgb_mat.min (axis=1)
corpus["ens_lgb_range"] = corpus.ens_lgb_max - corpus.ens_lgb_min

# log-odds transforms (numerically safe)
def _logit(p, eps=1e-6):
    p = np.clip(p, eps, 1-eps)
    return np.log(p / (1-p))

for c in lgb_cols:
    corpus[c + "_logit"] = _logit(corpus[c].values)

Optuna · parallel · 60 trials

The SUPER-ENRICHED run uses Optuna with the persistent SQLite study pattern. Four parallel workers, four threads per worker, sixty trials. The search space is deliberately bounded around the v9.2 production hyperparams — this is not a fresh hyperparameter discovery, it is a refinement of the known-good region in the presence of the new feature block. 

# Optuna search space (bounded around v9.2 prod)
study = optuna.create_study(
    study_name="btc_v9_3_super_enriched",
    storage=f"sqlite:///{CACHE}/optuna_study.db",
    load_if_exists=True,
    direction="maximize",
    sampler=optuna.samplers.TPESampler(n_startup_trials=8, seed=42),
    pruner=optuna.pruners.MedianPruner(n_warmup_steps=5),
)

def objective(trial):
    params = {
        "num_leaves":        trial.suggest_int("num_leaves", 31, 127),
        "learning_rate":     trial.suggest_float("learning_rate", 5e-3, 8e-2, log=True),
        "feature_fraction":  trial.suggest_float("feature_fraction", 0.65, 0.95),
        "bagging_fraction":  trial.suggest_float("bagging_fraction", 0.7, 0.95),
        "min_data_in_leaf":  trial.suggest_int("min_data_in_leaf", 40, 400, log=True),
        "reg_lambda":        trial.suggest_float("reg_lambda", 1e-3, 10.0, log=True),
        "num_threads":       4,
    }
    return walkforward_score(params, X_super, y, folds)

Hypothesis under test

That a small ensemble of prior-generation predictions, expressed as feature inputs to the new model, lets Stage B learn disagreement patterns — cases where v9_1 and v9_2 split, or where the meta-gate disagrees with the direct LGB. Disagreement is information.

The risk: feature explosion past 100 with only ~20k windows of training data per fold. The bounded hyperparam search exists precisely to keep regularisation tight enough that the bonus block helps rather than overfits.

The trial table will land in /tmp/btc_v9_3/optuna_trials.csv and the winning hyperparams in v9_3_OPTUNA_BEST.csv. If they beat the META configuration in walk-forward and survive a held-out sanity check, that becomes the deploy candidate.

09 · Deploy

The two-PR deploy pattern.

A v9.3 BTC deploy is not "drop a model into the engine and watch it score". The engine has no LightGBM in it. All inference happens on the timesfm-service side. Shipping the new model therefore requires changes in two repos, in a specific order, and on the right base branch.

Repo 1 · timesfm-service

The model itself lives here. The new scorer wraps the BTC v9.3 artifact, exposes the same input contract as v9.2, and emits the new feature columns the engine doesn't yet know about. The training corpus is btc_corpus_ENRICHED.parquet (108.8 MB). After Optuna finishes converging, the winning model gets serialised and committed alongside the scorer.

  • new scorer module — mirrors v9_2_scorer.py structure; loads the trained LightGBM heads; adds the Tier 1+2+3 feature computation in pre-process.
  • tick → feature transform — the six nested_5m_* aggregates need a streaming implementation. Per-window rolling buffers, recomputed on each tick.
  • schema bump — six new output columns on the scorer response so the engine can pick them up downstream.
  • backward compat — v9.2 stays operational. v9.3 ships behind a feature flag and emits in parallel until shadow-mode metrics confirm parity or better.

Repo 2 · novakash engine

The engine has to be taught about the new output columns and the new strategy wiring. This is the larger of the two PRs — the scoping agent estimated ~2,680 LOC including tests — and it mirrors the structure of the v9.5 ETH PR almost line-for-line.

  • column migration — six new columns in signal_evaluations, plus the OOF buffer columns needed for Stage A → Stage B (if META is in scope).
  • strategy YAML + .py hook — define v9_3_btc_lgb and (if META makes the cut) v9_3_btc_meta; LIVE thresholds stay UP 0.72 / DOWN 0.20 until we have shadow numbers that justify a re-tune.
  • ensemble writer wiring — pass the new probability fields through into window_evaluation_traces.surface_json so the JSONB-side analytics still work.
  • base branch — pr570, not main. Main has been four months stale relative to the live deploy stack; basing off it would force a massive rebase.

No auto-promote · house rule

10 · Roadmap

What's next.

Three lanes, ordered by ratio of probable lift to engineering cost.

Lane 1 · Tier 4 & 5 features

Tier 1+2+3 was the cheap layer. Tier 4 reaches into the raw microstructure stream: vpin_60s, gamma_short, gamma_long, clob_imbalance, top-of-book skew. These exist on the v3 composite tick stream but are not currently joined onto the windowed corpus. They will require a proper ASOF join with tight tolerance (1–3 s, not 30 s) to avoid the stale-feature trap from Section 4. Estimated lift: +2 to +5 pp on the lower-confidence threshold cells, where microstructure carries the most marginal information.

Lane 2 · Engine refactor for META

Stage B's +11.6 pp at DOWN 0.20 is sitting on the shelf until the engine learns to compute meta-features per tick from a rolling OOF buffer. The v9.5 ETH PR already established this pattern. Porting it to BTC is well-defined work — new buffer columns, new tick-level transform, the rest is plumbing — and the payoff is the largest single number in this entire chapter.

Lane 3 · XRP v9.5

XRP currently runs the same v9.2-style pipeline. The lessons from this BTC work port directly: enriched feature recipe, walk-forward CV, meta-stage when the engine supports it. The XRP corpus is materially smaller, which means regularisation becomes the variable to watch — less data, fewer Optuna trials in the bounded region, tighter validation discipline.

Risk register

  • stale microstructure joins — Tier 4 will repeat the Section 4 mistake if tolerance is too loose. Hard cap at 3 s for any new ASOF join.
  • meta train-serve skew — the engine refactor cannot ship until the per-tick OOF buffer is provably equivalent to the offline groupby. Build a parity test before flipping the flag.
  • SUPER-ENRICHED overfit — 16 bonus features on ~20k-window folds is feasible but not generous. Watch fold-to-fold variance; if it doubles relative to ENRICHED, drop the bonus block.
  • Polymarket autoredeem visibility — separate hub-side fix to log redeemed wins. Until it ships, every shadow comparison has to be evaluated against the (still hidden) true WR via post-event reconciliation.
