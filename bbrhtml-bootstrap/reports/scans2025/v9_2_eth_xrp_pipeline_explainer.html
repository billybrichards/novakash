1 · The TL;DR in one paragraph

We trained per-asset LightGBM heads for ETH and XRP using ~10 days of pre-computed features that already exist in the ticks_v2_probability.features JSONB column. The model is good. But to get more training data, we'd need to replay the feature pipeline against historical raw ticks — and the feature pipeline isn't a pure function. It's wired into the live FastAPI service via five in-memory caches that get fed tick-by-tick by background pollers. So "run it offline on March data" doesn't work. That's the cache issue.

2 · How the v9.2 ETH/XRP pipeline actually runs at serve time

The score we just got live (probability_lgb_v9_2_eth = 0.103 on a recent snapshot) came out of this exact path:

PriceFeed ring buffer · Binance WS for ETH/USDT spot, last ~120s of 1Hz prices stateful — populated by app/binance_trades_feed.py async poller
V2FeatureCache · per-asset rolling buffers: ret_60s, ret_300s, vol_std_pct, vpin_ewma12/60, delta_ewmaXX stateful — populated by app/v2_feature_cache.py, fed by price + Coinglass + Tiingo + Chainlink pollers
TimesFM forecast cache · the 9 tfm_* quantile features (p10/p50/p90/skew/spread/confidence/tail_risk/quantile_ratio/predicted_close) stateful — TimesFM model + LoRA classifier head runs every 30-60s in background
VPIN volume clock · vpin_sg + vpin_roll_std20, computed by walking through binance trades into volume-bucketed buy/sell flow stateful — accumulator over the last N trade-volume-buckets, can't reconstruct without trade-by-trade history
Smoothing buffer (v5) · Savitzky-Golay smoothing on derived signals stateful — needs N preceding samples to produce a smoothed value at time t
V2Scorer._assemble_features (app/v2_scorer.py:1071) · reads from all 5 caches above + adds Coinglass funding/OI/taker via app/v5_feature_loader.py runs every snapshot tick (~once every 2s during a 5m window's resolution)
v9.2 ETH booster (lgb_eth_<Δ>.txt) · per-delta LightGBM head selected by seconds_to_close bucket routed via the asset-aware path in app/v5_feature_loader.py (PR #155)
Per-delta isotonic calibrator (isotonic_eth_<Δ>.json) · piecewise-linear monotone map raw_prob → calibrated_prob paired with the booster at load time by V2ModelRegistry
probability_lgb_v9_2_eth → /v4/snapshot · emitted as field on the timescale payload, persisted into surface_json + (soon) signal_evaluations.probability_lgb_v9_2_eth

3 · The train/serve feature asymmetry

Training time

Read the features JSONB column from ticks_v2_probability — already materialised by past serving runs.

One row per (asset, window_ts, seconds_to_close). Each row has the full 58-feature dict captured at score time.

Pure pandas + LightGBM. No state, no async, no time travel. Just a snapshot of what the live scorer saw, written to disk at the time.

Source: training/eth_xrp_dataset.py in PR #153.

≠

Serve time

The 58-feature dict is computed on the fly by walking five stateful in-memory caches that are fed tick-by-tick by background asyncio pollers.

Can't be reproduced without playing back the entire feed history into those caches in the correct order.

This is the "cache issue" — the feature pipeline is a function of process state at time t, not just the timestamped raw data on disk.

Source: app/v2_scorer.py:1071 + 5 cache modules.

4 · Why "build a v2 training corpus" got blocked

To extend the corpus we'd need to either (a) replay the feature pipeline offline against historical raw ticks, or (b) wait for more pre-computed feature rows to accumulate organically in ticks_v2_probability.

Blocker A
The TVP feature pipeline is not separable from the live serving path. V2Scorer._assemble_features reads from 5 stateful in-memory sources fed by background asyncio pollers. There is no compute_features(window_ts, raw_ticks) → dict entry point. Refactoring it offline-runable is multi-day surgery on production-serving code — out of scope.
Blocker B
The raw upstream ticks for ETH/XRP only go back 19 days, not 71. Even if we built the offline replay, we'd hit a hard wall at 2026-04-29. The labels (market_data.outcome) go back to 2026-03-06 — 73 days. But the features driving the model (ticks_chainlink, ticks_tiingo, ticks_coinglass, ticks_gamma for non-BTC) only start on 2026-04-29.
Blocker C — most decisive
ticks_binance is BTC-only. The 1Hz Binance price stream that the TimesFM classifier head (the strongest feature group for ETH/XRP per the importance ranking) needs as input was never persisted for ETH/XRP. Live WS feeds run in-process but trades aren't written to disk. So the strongest features can't be reconstructed historically at all.

5 · Why the v1 model still works at 10 days

The v1 corpus is thin (10 days, 1,340 windows × ~290 ticks each = 393k feature rows). But it's real: those are actual live-serving snapshots of (feature, outcome) pairs. The model learned to predict UP-vs-DOWN at window close from the same features the live scorer feeds it now. Train/serve skew is zero by construction — both use TVP JSONB.

Why v1 is shippable despite thinness
At conservative thresholds (e.g. ETH DOWN p ≤ 0.04 in eval_offset [120, 210]), v1 emits a real calibrated probability with ~23 fires/day at ~93.8% projected WR on the held-out test split. That's a real signal — just measured on a thin baseline. Shadow mode at $5 max position cap collects more honest fire-level data without exposing real capital, while we accumulate more TVP rows organically.

9 · The deploy chain — Option A pattern

Same gated procedure each time we ship per-asset emission:

  1. You authorise the chain with explicit phrasing naming the production targets.
  2. I merge the PR.
  3. Build deploy tarball from main HEAD, upload to s3://.../deploys/.
  4. SSM tag rollback image on classifier-gpu (i-0f77468732c4d8250).
  5. SSM backup /home/ubuntu/timesfm-service → .before-<deploy_id>.
  6. SSM download tarball + extract + verify new code.
  7. SSM rsync -av (no --delete!) into place + chown.
  8. SSM .env append: V9_2_<ASSET>_ENABLED=true.
  9. SSM docker compose build (with --gpu.yml overlay).
  10. SSM up -d --force-recreate. Verify field appears in snapshot.
Recurring gotcha
docker compose restart does NOT reload .env. Only up -d --force-recreate does. We hit this on the v9.2 iso deploy earlier in the session — the env flag was true in .env but false in the container env until we recreated. Now baked into the standard procedure.

Why both can run inside the 2s snapshot budget
Each scorer has its own V2ModelRegistry instance + its own V2Scorer, wrapped in independent asyncio.wait_for(..., timeout=2.0) blocks. They run concurrently — total latency is max(legacy, new), not legacy + new. Either crashing doesn't take the other down.

12 · The multi-month silent persistence gap (fixed by PR #559/#560)

Discovered by inspecting the 2026-05-18 parquet snapshot:

TableBTC 5mETH 5mXRP 5mETH 15m
signal_evaluations518k ✓0 ✗0 ✗0 ✗
window_evaluation_traces541k ✓0 ✗0 ✗426k ✓
ticks_v2_probability1.24M ✓419k ✓419k ✓(no timeframe split)

The model has been firing into /v4/snapshot for ETH/XRP 5m for months — but only ticks_v2_probability caught it. The engine-side writer that fills signal_evaluations + window_evaluation_traces never ran for non-BTC 5m. This is exactly the persistence gap PR #559 (ETH) + #560 (XRP) fix.

Why this matters more than I framed it earlier
PR #559/#560 aren't just "adding a v9.2 field" — they're fixing a months-old persistence gap by enabling the writer to handle non-BTC 5m at all. Once they deploy, signal_evaluations starts catching BOTH the legacy probability_up AND the new probability_lgb_v9_2_eth for every ETH 5m window. Same for XRP. This makes future WR audits + meta-gate retraining for alts possible.
