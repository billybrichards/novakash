02 · how we got here

v9.4 in 90 seconds.

A trading model is a probability factory. It takes in features — recent price moves, order-book imbalance, funding rates, oracle prices — and outputs a number between 0 and 1. 1.0 means "I am certain ETH will close higher than where Polymarket says it should". 0.0 means certain DOWN. 0.5 means coin flip.

You then set thresholds. Bet UP when probability ≥ 0.82. Bet DOWN when ≤ 0.23. Otherwise abstain. The trick is making the probability honest. If your model says 0.82 but it's really only 0.55, you're going to lose a lot of money fast.

The chapter you're reading is the story of three days of that process — the lessons, the failures, and the v9.5 sprint that should start when this finishes loading.

03 · the engine

Forests of friends.

The model that does the actual predicting is called LightGBM. Before we explain it, forget about ML for a second. Imagine you have 200 friends, and each one is going to make a single yes/no guess about whether ETH closes UP or DOWN in the next 5 minutes.

Each friend follows a flowchart. Is the chainlink price above 2125? Yes → is the hour above 12? Yes → is funding negative? No → predict UP. Each flowchart is called a decision tree. The friend's vote is the leaf they land on.

You trust the majority vote across all 200 friends. That's a random forest — well, almost. LightGBM does something cleverer.

how 200 friends decide UP or DOWN

Step 1 · trees vote

Each tree asks a small handful of yes/no questions about the features (price, volume, oracle, time, etc.) and lands the example in a leaf. The leaf has a number. That number is the tree's contribution to the final probability.

Step 2 · boosting

Here's the clever bit. Tree 1 is built by training on all the data. Tree 2 is then built specifically to fix the mistakes Tree 1 made. Tree 3 fixes the mistakes of Trees 1+2. And so on, for 200 trees. This is called gradient boosting.

It's like a relay race where each runner only sprints during the gaps the previous runners left.

Step 3 · LightGBM specifically

LightGBM is Microsoft's open-source implementation of gradient boosting. It's the one we use because:

  • FastIt trains 30 boosters across 5 folds in 13 seconds on a 16-core CPU. No GPU required for tabular data this size.
  • Handles missing dataIf a feature is NaN, LightGBM routes that row through a "missing" branch in each split. No fragile imputation needed.
  • Leaf-wise growthMost tree libraries grow level-by-level. LightGBM grows the leaf with the largest loss reduction first, which is more efficient.
  • InterpretableYou can ask the model "which features mattered most?" and it returns a ranked list of feature gains. We'll look at v9.4's gains in the next section.
  • BoringThis matters. LightGBM has been around since 2017. It's a known quantity. No surprises in production at 3am.

The 10 feature families

The categories below aren't just for charting — they correspond to independent data sources. We'll come back to this in the v9.5 plan, because the way to make models more robust is to add features from genuinely independent sources, not stack more correlated ones.

TFM9 features
A TimesFM 2.5-200m neural net runs on the recent Binance tick history and emits quantile forecasts (p10, p50, p90), confidence, and skew. Then a LoRA classifier head re-shapes that into something useful for our problem.
Coinglass16 features
Open interest, funding rate, long/short ratio, top-trader positioning, liquidations, taker buy/sell volume. The microstructure of futures positioning across major exchanges.
VPIN4 features
"Volume-synchronized probability of informed trading." A short-horizon flow imbalance signal — when smart money is buying or selling aggressively, VPIN spikes. We use 4 smoothed variants (EWMA12, EWMA60, Savitzky-Golay, rolling std 20).
Delta8 features
"How much has price moved." We smooth Binance / Tiingo / percentage deltas with EWMAs at 12s and 60s and rolling std. Captures short and medium momentum.
v2 logit2 features
A previous-generation prediction (v2_probability_up) re-emitted as a logit, with two smoothing windows. The model can use it as a noisy hint or override it.
Time5 features
Hour-of-day, day-of-week, minute, session bucket (asian/european/us), and eval_offset (how many seconds into the window we're scoring). Markets have time-of-day personality.
Price5 features
Current Binance price, price 60s ago, Chainlink price, return since window open, and the 60s return. The basic "where are we, where have we been" signals.
Volatility2 features
Standard deviation of returns over the 5m window and the price range as a percentage. How chaotic the window is.

How much do Chainlink and Binance disagree (cross-source divergence)? How calibrated is the TFM spread? These are sanity-check features — the model treats wide divergences as warning signs.

Polymarket's own implied probability that ETH closes UP for this window, plus market vig and spread. Captures "what the crowd thinks". Backfilled today from 1 day of coverage to 22 days.
05 · v9.5 new idea

When the model can't decide.

Here's an idea we're testing in v9.5. The model emits a fresh probability every ~2 seconds during a 5-minute window — so by the time the window closes, it has produced ~150 probability values for that single window.

Most analysis ignores this. We just take the latest probability and bet on it. But ask yourself this: if those 150 values were stable (model gradually moving from 0.85 → 0.92) versus oscillating (model bouncing 0.45 → 0.65 → 0.40 → 0.70 → 0.55), should you trust the final number equally? Of course not.

The number of times the model's probability crosses 0.5 within a window is a measure of its own indecision. Few crossings means high conviction. Many crossings means the model is genuinely uncertain even though its final number landed on one side. This is a meta-feature — a feature about the model's own behavior.

why this is called a meta-feature

Most features describe the market: "what is the price doing, what is funding doing". A meta-feature describes the model itself: "is the model being consistent, or flip-flopping". You can think of it as the model's own confidence-of-confidence signal. We can use it as a gate: only fire the bet if the model has been on the same side of 0.5 for the last 30 seconds.

Computing this is a SQL window function — Postgres can do it directly against signal_evaluations:

SQL 
-- For each window, count how many times the predicted probability
-- crossed the 0.5 line. Plus the longest stable streak.
WITH ordered AS (
  SELECT
    window_ts,
    evaluated_at,
    probability_lgb_v9_2_eth AS p,
    LAG(probability_lgb_v9_2_eth) OVER (
      PARTITION BY window_ts ORDER BY evaluated_at
    ) AS prev_p
  FROM signal_evaluations
  WHERE asset = 'ETH'
)
SELECT
  window_ts,
  COUNT(*) FILTER (
    WHERE (p >= 0.5) <> (prev_p >= 0.5)
  ) AS p50_crossings,
  STDDEV(p) AS p_std_within_window,
  MAX(p) - MIN(p) AS p_range
FROM ordered
GROUP BY window_ts
ORDER BY p50_crossings DESC;
06 · methodology

How we stopped lying to ourselves.

The reason v9.2 got demoted is that we measured it wrong. For a long time we'd been training on the first 70% of the data, validating on the next 15%, and testing on the last 15%. One cut. One number. 92% UP win rate. Big sigh of relief, ship.

The problem: that 92% came from a single test window. 2026-05-17 was a lucky day. The day before would have given 87%. The day after would have given 81%. By taking one number from one window, we hid all the variance.

Walk-forward CV fixes this. Instead of one cut, we train and test across five expanding windows, each holding out a different 3-day test slice. We report the mean WR and the standard deviation across folds, plus the worst-fold WR.

the old way · single chronological split

One window. One number. Liar.

"We measured the bullseye, not the spread of the arrows around it."
the new way · 5 expanding-window folds

Five windows. Five numbers. Mean ± std.

"Each fold's test window is a different regime. The model has to win across all of them or we know it's brittle."

The kicker: Fold 4's test window was today — 2026-05-20 16:45 → 2026-05-21 15:45 UTC. The same regime-shifted day that caught v9.2 out yesterday. Walk-forward CV literally measured the model's performance on the day that would later catch it.

At loose thresholds (p≤0.45) Fold 4 scored 52.87% WR — basically matching the 67% v9.2 delivered live. At tight thresholds (p≤0.23) Fold 4 abstained entirely from DOWN bets. The model knows what it doesn't know — we just have to listen.

07 · the threshold cliff

Where the model finds its edge.

Let's plot the WR at every threshold the model could fire at. UP side on the left, DOWN side on the right. Each point is the mean WR across the 5 walk-forward folds, with a shaded band showing the standard deviation.

Notice the shape. At loose thresholds (UP p≥0.70, DOWN p≤0.45), the WR is around 88% / 74% with a wide variance band. At tight thresholds (UP p≥0.82, DOWN p≤0.23), the WR climbs to 93% / 91% and the variance band collapses to nearly invisible.

The model isn't lying — it's telling you exactly when to trust it. At the edges, it's confident. In the middle, it isn't. Setting your firing threshold at the cliff edge is the entire game.

UP side
fire when p ≥ threshold · n fires per fold
DOWN side
fire when p ≤ threshold · the cliff is at 0.27→0.25
the lesson, distilled

Most ML practitioners optimize for the highest mean accuracy. In trading, you optimize for the highest accuracy at acceptable variance. A model with 91% WR ± 1pp beats a model with 95% WR ± 8pp every time, because the second one can have a day where it goes 70%, and that day will end your career.

08 · is it real?

Is this edge real or just lucky?

Important caveat: walk-forward CV across 5 folds is more honest than single-day held-out, but it's still a small sample. 4,898 DOWN fires at p≤0.21 across 5 folds is about 980 per fold. We need actual significance tests to claim an edge.

Two-proportion z-test

The simplest test: is our 91% WR significantly different from the 50% base rate of a coin flip? If we observe k wins in n bets, the z-statistic vs base rate p0 is: 

z = (p_hat - p_0) / sqrt(p_0 * (1 - p_0) / n)
p_value = 2 * (1 - Φ(|z|))

For 91% WR on 980 bets vs base 0.50: z ≈ 25.7, p < 0.0001. Comically significant. The interesting test is vs a 90% target — are we statistically beating 90%? z ≈ 1.0, p ≈ 0.32. Not significant. Same WR, different question.

Bootstrap confidence intervals

Instead of trusting a single point estimate, resample the bets with replacement 10,000 times and look at the distribution of WRs. The 2.5% and 97.5% percentiles give a 95% CI without assuming normality. 

import numpy as np
wins = np.random.binomial(1, 0.91, size=980)  # your actual bets
boots = [np.mean(np.random.choice(wins, len(wins),
        replace=True)) for _ in range(10_000)]
ci_lo, ci_hi = np.percentile(boots, [2.5, 97.5])
# example: (0.892, 0.926) — 95% CI on the WR

v9.4's DOWN @ p≤0.21 across 4,898 fires gives a CI of roughly (0.910, 0.926). That CI is entirely above 0.88, which means we can claim >88% WR with 95% confidence. We can't claim >92%.

Calibration & ECE

A separate question: when the model says 0.80, do 80% of those bets actually win? That's calibration. The Expected Calibration Error (ECE) bins predictions and measures the gap between predicted and observed accuracy in each bin.

v9.4's reliability line tracks the diagonal closely — when the isotonic calibrator says 0.80, the realized win rate really is ~80%. ECE of 0.034 means the average gap between predicted and realized is 3.4 percentage points. Below 0.05 is considered well-calibrated for production.

09 · the experiments map

When more data hurts.

A short tour of the v9.4.x experiments we tried today before settling on the baseline. Each row is a separate model trained on the same 22-day corpus with the same walk-forward CV, just with different feature additions.

The instructive thing isn't that v9.4 baseline won — it's how the others lost. They didn't fail by reducing mean WR. They failed by blowing up the variance. Mean WR stayed similar, but the worst-fold WR collapsed.

Why "right-feeling" features failed

Both priceToBeat and chainlink seemed like obviously good additions. priceToBeat is the resolution threshold — without it, the model has to learn the threshold implicitly. Chainlink is the oracle price — adding chainlink-based deltas should give the model a more accurate reference.

What went wrong:

  • priceToBeat made the model overconfidentThe model saw "current price relative to threshold" and got bolder at tight thresholds. On regime-shift days (where intra-window momentum doesn't follow recent patterns), that bolder confidence cost us.
  • Chainlink heartbeat stalenessChainlink Streams publishes on price-change-threshold, not every tick. When stale, the "Binance − Chainlink" delta accumulates artificially. The model learned the artifact, fired sharp DOWN bets, and got destroyed on one fold (100% wrong).
  • Coverage gaps create two-mode learningAt 54% PTB coverage, the model learned different behavior for "PTB present" vs "PTB absent" rows. Neither mode was robust.

The fix is path-dependent feature engineering — TWAP-since-PTB, # crossings of PTB, max excursion, distance normalised by realised vol. These are v9.5 work.

10 · v9.5 architecture

Three signals. One model.

The principle for v9.5 isn't "add more features". It's "add features from independent data sources". Stacking correlated features (Binance delta + Binance EWMA delta + Binance Savitzky-Golay delta) gives you diminishing returns. Stacking independent sources reduces variance super-linearly.

We're targeting three layers of signal: microstructure (what the order book is doing), oracle (what the resolution sources say), sentiment (what the crowd thinks).

ring 1 · microstructure

What the book is doing.

Top-of-book pressure, depth imbalance at multiple bands, taker-side flow. Captures supply/demand at the price level.

  • Binance ticks (have)
  • Binance depth book (collecting)
  • VPIN (have)
ring 2 · oracle

What resolves the bet.

Chainlink Streams + Tiingo are what Polymarket uses to decide the outcome. Our model should track these directly, with freshness gates to avoid stale-tick contamination.

  • Chainlink price (have)
  • Chainlink staleness (v9.5)
  • Tiingo last_price (have)
ring 3 · sentiment

What the crowd thinks.

Polymarket gamma is the implied probability the crowd is willing to bet. Polymarket CLOB book is the slope of that opinion. Coinglass positioning is leveraged sentiment.

  • Polymarket gamma (backfilled)
  • Polymarket CLOB (collecting)
  • Coinglass (have)
why three rings, not one

Each ring is statistically independent from the others. When Binance depth disagrees with Polymarket gamma, that disagreement itself is signal. A single-source model can be wrong-footed when its source is in a weird state. A three-source model rarely has all three sources in the same wrong state at the same time.

10½ · refining the target

Max n at ≥90% WR.

Before we build v9.5 we need to be precise about what we're optimising. The first instinct is "highest possible win rate." That's wrong. The right target is the most bets we can fire while keeping the realised WR at or above 90%.

Why? Because a 95% WR strategy that fires 5 times a day makes less money than a 91% WR strategy that fires 50 times a day, assuming similar bet sizing. We want a Pareto-optimal operating point, not a perfectionist one.

v9.4 already has several candidate operating points on that Pareto front. Here are the v9.4 walk-forward CV numbers re-sorted by max-n-at-≥90%-WR:

The optimisation target for v9.5 is to push the entire WR-vs-n curve up and to the right. Specifically: increase mean WR at a given threshold so that LOOSER thresholds become viable (more fires) without breaking the ≥90% constraint.

If we can pull UP @ p≥0.78 from 91.68% mean / 87% worst-fold up to 92%+ mean / 90%+ worst-fold, we unlock ~320 more fires per day at honest 90% WR.

Stretch goal: the long-horizon heads

There's a separate question: can v9.5 predict UP/DOWN earlier in the window? Each window has 6 per-delta heads — at delta=30s we're scoring near window close (most of the window has already happened), at delta=240s we're scoring just 60 seconds in (very little has happened yet). Per-head accuracy in v9.4 looked roughly like:

why t-200 to t-160 matters

At the start of a window the model knows almost nothing — the underlying price has had ~60 seconds to move. Most of the information about whether ETH closes UP comes from events that haven't happened yet. The longer-horizon heads (delta=180s, 240s) are predicting further into the future. Better here means betting earlier, which means more time in market, which means more total trade volume.

We're not going to solve this in v9.5. But every workstream — Binance depth, Polymarket CLOB, TFM forecasts — provides forward-looking information that should help the long-horizon heads more than the short-horizon ones. We'll track per-delta WR separately as the v9.5 ablations land.

v9.5 starts without LoRA

One operational decision worth flagging: the BG agent that recreated our TimesFM inference file ran the base TimesFM-2.5-200m model with no LoRA adapter applied. The only adapter on S3 is a BTC fine-tune; applying a BTC-trained adapter to ETH would be out-of-distribution.

That means the tfm_* features going into v9.5 are uncalibrated zero-shot quantile forecasts, not the LoRA-discriminated signals we'd ideally have. LightGBM will downweight them automatically if they're not informative. If v9.5 ablations don't lift mean WR, we'll A/B against the BTC-adapter version as a follow-up experiment.

13½ · the dedup lesson

When WR is a lie.

After Step 1 of v9.5 we got walk-forward CV results showing 96-98% UP WR. We almost shipped that number. Then we ran a deduplication analysis — and discovered the WR was being inflated by a counting artifact.

The cross-validation reports WR across (window_ts, delta_seconds) rows. Each window has 6 delta heads. The model can fire on a window via multiple deltas. The CV counts each as a separate "fire". So a window where the model is right at 4 of 6 deltas counts as 4 "wins" — even though in production we only place ONE bet per window.

Worse — we then synthesised the per-tick (every 2s) prediction grid for v9.5.0 across the full 22-day corpus. ~840k synthesised emissions. If you count those PER-TICK, the model often fires 60+ times within a single window once it crosses the threshold. The per-tick WR looks great. The per-window WR is much lower.

Deployment design — single-model vs stacked

The dedup finding has architectural implications for v9.5.1 deployment, which the current engine isn't set up for. Three patterns we considered:

v9.5.0 — drop-in replacement

A
Same engine pattern as v9.4 deploySingle model, one LGB inference per tick. Engine writes probability_lgb_v9_5_eth to signal_evaluations. Strategy gates on tight thresholds (UP p≥0.96, DOWN p≤0.04).
B
Production-ready todaySame S3 flip pattern (current.json swap), same runtime_overrides table, same engine code path. We ship today's session.
C
Estimated effect: ~100 fires/day at 90-92% WRvs v9.4 LIVE's 49 fires/day at 89.8%. 2x volume, similar WR — that's real lift.

v9.5.1 — stacked, needs engine refactor

A
Two-stage inference per tickv9.5.0 fires every 2s and accumulates predictions in a per-window buffer. v9.5.1 reads the buffer, computes meta features (p_mean, p_std, n_crossings, etc.), then makes its own prediction.
B
Cold-start: meta needs ~30 emissionsThat's ~60s of v9.5.0 history. So v9.5.1 can only produce meaningful predictions from t = window_open + 60s onwards. The first 60s of every window is v9.5.0-only.
C
Engine work neededPer-window buffer, two model inferences, two probability columns in signal_evaluations, new strategy that reads probability_lgb_v9_5_1_eth. ~1-2 days of engine PR.
D
Validation gateBefore shipping v9.5.1, deploy it in GHOST mode side-by-side with v9.5.0 LIVE. Compare per-window WR on actual production data for 48h before promoting. The dedup lesson taught us not to trust CV numbers blindly.
why this matters for the architecture

The principle: a model that uses meta-features about itself is a stacked model. Stacking can give real lift but creates new deployment patterns. The engine needs to maintain state across emissions (the per-window buffer), and the strategy needs to wait for a warm-up period before trusting v9.5.1's output. None of that exists today.

Ship v9.5.0 first. Build the stacking infrastructure as a separate engineering project. Then v9.5.1 becomes a feature flag flip, not a model swap.
