01 · The trigger

A few extra losses.

The question arrived informally. iso_expand — the v9.2 BTC isotonic-recalibrated strategy that had been carrying the live BTC leg for weeks — had logged a string of losses that didn't quite feel like noise. The threshold was holding, the model was emitting, but the win rate had drifted just enough to be visible above the bar.

"Can we improve v9.2 BTC?" That was the prompt. Five words. No formal ticket, no migration plan, no shadow-mode acceptance criteria. Just a question.

By dawn, that question had touched every asset the system tracks. A new v9.3 BTC base model trained on a walk-forward corpus 18× the size of the original v9.2 single-split. A new v9.5 ETH emission path wired end-to-end and deployed. A v9.5 XRP corpus rebuilt twice — first on a 3.5-day skeleton that the walk-forward CV refused to even run on, then on an 8.62-day version that exposed an honest WR ceiling almost ten points below v9.5 ETH. And in between, a thirty-minute incident where every probability the system emits went dark.

Nothing about the prompt suggested any of that. The night unspooled because each finding implicated the next. The v9.3 BTC walk-forward revealed that v9.2's headline 95% WR was inflated by a tiny test slice (n=161 windows) — which meant the v9.4 ETH and v9.5 ETH numbers probably had the same problem, which meant we needed to ship the v9.5 ETH emission path tonight so the 24h GHOST window could start counting, which meant the v3 box deploy plan from memory needed to be re-checked, which is when we found the box had been stopped for 14 days, which is when we found the disk problem on its replacement…

The way you find out your infrastructure is fragile is by trying to ship through it at three in the morning. — field note, 2026-05-23

This chapter follows the night chronologically. The numbers are pulled from the run artefacts: /tmp/btc_v9_3/*.csv, /tmp/xrp_v9_5_cache/*.csv, the public.notes RDS table (rows 585 → 595), the merge reports filed to /tmp/v9_5_*_report.md, and the SSM deploy logs caught mid-flight.

02 · The data infra unlock

DuckDB plus psql COPY.

Before any of the models, the night turned on a small infrastructure reframing. Pulling enough training data through the SSM tunnel had stopped being possible the canonical way.

The previous pattern — asyncpg over the SSM port-forward at 127.0.0.1:15432 — had worked for the small TVP slices the audit-#391 pipeline expected. Tonight's pulls were bigger. The XRP corpus build hung silently inside asyncpg.fetch on the first 1-day chunk, with the kernel buffer pinned at 164 MB and 9 minutes of idle TCP time. The wait_for(120s) guard never fired. The process sat in D state with no bytes moving until killed.

The fix was to stop trying to bulk-pull through asyncpg. The pattern that worked was a hybrid: bulk via DuckDB reading the daily S3 parquet export, delta via psql COPY through the SSM tunnel in small chunks.

The pipeline that worked

  1. Bulk: DuckDB read_parquet('local-2026-05-18.parquet') → 1,340 windows / 393,315 rows / 5.34d in 2.7s.
  2. Delta: psql -h 127.0.0.1 -p 15432 -c "COPY (SELECT … WHERE window_ts BETWEEN $1 AND $2) TO STDOUT" in 2-hour chunks. Eight chunks at 80-130s each, 165 windows / 62,224 rows.
  3. Merge: pandas concat on (window_ts, delta_secs) → 1,505 windows / 441,022 rows / 8.62d total.
  4. Enrich: JSONB features → 53 flat float32 columns; 9 v9.5-NEW keys NaN-filled (no engine emitter for XRP); gamma 5 NaN-filled (XRP gamma is 15m-only).

The rule that emerged: for any pull above ~100k rows, asyncpg through SSM is unreliable. Use DuckDB on the daily parquet export for bulk and psql COPY for the delta. The parquet export already exists; the daily writer dumps to S3 at 04:00 UTC. The SSM tunnel only has to carry the tail.

Pull pattern · bulk + delta + combine
why a hybrid beats either path alone

The lesson generalised. The exact same pattern — bulk DuckDB + delta psql COPY — was what built the XRP corpus an hour later, and the v9.3 BTC walk-forward corpus earlier in the night. The asyncpg path was retired for any pull touching more than a day of TVP data. The SSM tunnel survived; the strategy on top of it didn't.

Operating heuristic
For < 100k rows: asyncpg over SSM is fine. For ≥ 100k rows: pull bulk via DuckDB from the daily S3 parquet, top up via psql COPY in 2h chunks. The mistake was assuming asyncpg's wait_for guard would catch the stall — at network level the bytes were flowing into the kernel buffer just fine, so neither side knew the application layer was stuck.
03 · The v9.3 BTC story

The walk-forward revelation.

Chapters 14·pt1 and 14·pt2 covered v9.3 BTC in full. This is the condensed inline of the result so the rest of the night reads coherently — and so the pattern that exposed v9.2's inflated WR sits next to the patterns that would soon do the same to ETH and XRP.

Walk-forward CV vs single-split

The original v9.2 BTC was validated on a single last-10%-of-corpus hold-out: 24 days of data, 90% train, 10% test. The test slice ended up containing 161 windows that scored above p ≥ 0.96. On those 161 windows the model logged a 95.0% win rate. That number went into the headline.

v9.3 BTC re-ran the same test with proper walk-forward CV: 5 folds × 4 days test, 24-day corpus, 5,702 windows total. At the same p ≥ 0.96 threshold, the WR landed at 91.3% on 1,488 windows. The model was about as good as v9.2 — it was the test geometry that had been lying.

TIER 1 + 2 + 3 enrichment

v9.3 added 23 new features in three tiers — Tier 1: nested 5m return / vol / VPIN summaries. Tier 2: source-quality and session-bucket. Tier 3: v3 column renames bringing the BTC schema into alignment with ETH/XRP. Net effect at LIVE thresholds: +7.2pp UP WR at p ≥ 0.72 vs v9.2 on the same walk-forward folds. The model is genuinely better, just not 95% better.

v9.4 META (deferred)

A v9.4 stack — meta-features computed from the v9.3 base probability trajectory across a window — added +11.6pp DOWN WR on the walk-forward CV. But the meta-features were computed using the full window's base-prob trajectory at training time, and only the past-only trajectory at serve time. The train-serve skew is unbounded and not yet quantified. v9.4 stays on the bench until the past-only retrain runs. The chapter 14·pt2 wrote it up; the gating decision stuck.

The per-tick / per-window distinction (why the headlines drift)

Both v9.2's and v9.3's threshold sweeps emit two WR numbers per threshold: tick WR and window WR. Tick WR counts every individual scoring event above the threshold and weights them equally. Window WR collapses every fire inside a single 5-minute window down to one outcome and counts that once.

The numbers look very different. At v9.3 BTC's p ≥ 0.96 on the walk-forward OOF: tick WR 96.5%, window WR 91.3%. A 5.2pp gap. The reason is that high-conviction windows fire many ticks — a window that's about to win at 0.96 conviction might fire 30 ticks above the threshold, all of which count toward tick WR. A window that's about to lose at 0.96 conviction might fire 5 ticks. Tick WR over-weights the wins because the wins are louder.

Per-window dedup is the honest accounting. v9.2 BTC's headline 95% was a per-window number — already deduped — but the test slice was only 161 windows. The single-split test had two problems compounding: the WR was honest but the sample was thin, so noise dominated. v9.3's walk-forward fixed both: same per-window dedup, but applied to 1,488 windows at the same threshold. That's the number we now quote.

The v9.3 BTC corpus exemplifies the data-infra pattern that section 2 introduced. The bulk slice came from a parquet snapshot (2026-05-18) joined to market_data.outcome via DuckDB. The delta — the post-snapshot 4-5 days — came via psql COPY in 2-hour chunks through the SSM tunnel. Combined:

The corpus has six Δ buckets per resolved window (30/60/90/120/180/240 seconds-to-fill), so the 5,702 windows translate to ~34k unique training rows per Δ-head once outcomes are joined and unresolved windows are dropped. The disk diagnosis

df -h on classifier-gpu came back with 114 GB used / 117 GB total / 99% full. Three GB of headroom. The TimesFM wheel is roughly 250 MB compressed but unpacks to ~900 MB; the pip install would have started, partially written, run out of disk, and silently truncated the package without raising. The image was built; the dependency was a husk.

docker image ls revealed why. Thirteen old image backups: gpu-gates-{date}, gpu-before-{date}, going back two months. Average layer size 15.3 GB. Combined, they were occupying ~200 GB of overlay storage on a 117 GB disk — heavily deduplicated because they shared base layers, but every --no-cache rebuild forked a new layer set that didn't dedup with anything.

Prod incident timeline · 2026-05-23 ~01:00–01:30 UTC
deploy → crashloop → diagnosis → prune → recovery

The prune

docker image prune -a --filter "until=336h" reclaimed about 35 GB. The thirteen gpu-gates-* / gpu-before-* tags went; the current latest tag and the rollback target stayed. Disk pressure dropped to ~70% used. Rebuild proceeded clean.

The second mistake (caught quickly)

The first rebuild used docker compose -f docker-compose.yml up -d. Container started. Probabilities emitted. But the V9_5_ETH_ENABLED=true flag wasn't honoured — the container was running on CPU-only profile, missing the GPU capability declarations that docker-compose.gpu.yml layers in. The fix was one line: docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --force-recreate. Two files, not one.

Lesson burned in: on classifier-gpu, every docker compose invocation needs both the base file and the GPU override. The deploy script in reference_v2_box_deploy.md documented this; the SSM send-command wrapper had dropped the -f docker-compose.gpu.yml override during the rebuild. Restored. The deploy script will get a guard.

Total outage window
~30 minutes from initial deploy attempt to all five probabilities back. During this window, /v4/snapshot for BTC, ETH, and XRP all returned probabilities with status ok but the probability_lgb_* fields were either None or stale values from a registry that wasn't being refreshed. The engine-side strategies degraded to SKIP (model_not_loaded), which is the safe failure mode — no incorrect fires were issued.

06 · XRP, twice

The asset that wouldn't cooperate.

XRP had never had a v9-series model. The v1 candidate from 2026-05-19 was offline-only — trained on 58 features, no S3 stage, no LIVE wiring, no walk-forward CV. The plan tonight was to skip v9.3 and v9.4 entirely and land XRP directly at v9.5-equivalent. That happened. Twice.

Attempt 1 · the 3.5-day skeleton

First pass burned ~30 minutes on the asyncpg dead-end (see section 2). What survived was a corpus built from the locally-available half of the 2026-05-18 parquet sync — the other half was still being throttled down from S3.

Numbers: 205,345 rows / 702 windows / 3.50 days / 0.487 UP rate. Walk-forward CV with k=5 × 2d test refused to even run — the guard span ≥ 2 × fold_test_days requires 4 days minimum, and 3.5 < 4. The training proceeded with default V5_LGB_PARAMS on the full corpus, no held-out, no hyperparameter search, no honest WR estimate. The artefacts landed at training/trials/2026_05_23_v9_5_xrp_production/ and uploaded to S3 at v2/xrp/xrp_5m/543b554_v9_5/..., but the pointer JSON was never updated. The "deploy" was just scaffolding.

Attempt 2 · the 8.62-day corpus with Optuna

After the prod incident wrapped up and the BTC+ETH probabilities were stable, the XRP build relaunched on the hybrid DuckDB+psql COPY pattern from section 2. Bulk in 2.7s, delta in eight 2-hour chunks. 1,505 windows / 8.62 days / 441,022 rows / 49.2% UP rate. The walk-forward CV now had headroom for k=4 × 1.5d folds. The honest estimation was unlocked.

Optuna · 40 trials

Optuna ran with the same search space as the BTC SUPER run, plus a new down_reweight axis specific to XRP. The best trial was #15 with composite 0.8943 — but only on the bulk-slice OOF. When the best params were re-run on the FULL 8.62d walk-forward, the WR dropped to ~80% per side. The 9-percentage-point gap was Optuna overfitting to the bulk slice — the only honest read of XRP's ceiling is the full-corpus number.

The two findings that mattered

First: XRP wants a milder down_reweight than ETH. ETH's 3.0× reweighting handled the asymmetric DOWN-side base rate. XRP's base UP rate is 49.2% — almost perfectly balanced — and trials with reweighting at 3.0× or 5.0× scored worse than 1.0× / 1.5×. The mild 1.5× reweighting won.

Second: shallow trees plus heavy bagging is universal. Both BTC's and XRP's best Optuna trials picked max_depth=2 (or near it) and bagging_fraction in the 0.74-0.80 range with bagging_freq=1. The signal in both assets sits in a small number of shallow feature interactions; deep trees overfit the per-window noise. This is a hyperparameter pattern, not an asset coincidence.

The temporal shape — XRP fires late

This was the most striking finding. BTC's median first-fire is at stc=274s — i.e. fires arrive 26 seconds past window-open and persist. XRP's median first-fire is at stc=154s for the raw threshold and stc=104s for the tight corner. XRP fires mid-to-late in the 5-minute window, exactly opposite BTC's early-fire pattern. The YAML eval_offset bands had to shift: BTC at [20, 170], XRP at [60, 240] / [120, 240].

Why XRP fires late · the temporal explanation

XRP's signal builds slower than BTC's. The fire-timing data below tells the story: BTC's tight strategy gets its first fire at stc=274s — about 26 seconds past window-open, the model has already locked in its conviction. XRP's tight strategy doesn't fire its first conviction-band prediction until stc=104s — i.e. about 196 seconds into the 300-second window.

The driving features explain it. BTC's top-importance features include nested_5m_ret, tfm_p10, and the v2_logit transfer — features that resolve early in the window because they're derived from the prior 5-minute close. XRP's top features are ret_since_window_open, cg_taker_net_usd, ret_60s, and cg_long_pct — features that need time within the window to accumulate signal. Returns since open need return data to accumulate. CG taker flow needs taker flow to arrive on the wire. The model has to wait.

Practically, this means the eval_offset band in the YAML strategies differs: BTC tight runs [20, 170] (early-window subsegment), XRP tight runs [120, 240] (late-window subsegment). The engine's gate evaluator only considers fires that arrive within these bands. Outside the band: SKIP cleanly, no fire.

Honest read
XRP at v9.5 architecture does not reach v9.5 ETH parity. ETH's walk-forward CV showed 90%+ pockets; XRP tops at ~83% UP / ~93% DOWN. The drivers are: corpus span (8.62d vs ETH's 22.66d), the same 9-feature NaN-fill gap (binance_depth_*, clob_pre_*) applied to both training AND serve, and an RDS horizon limit (~11d for XRP TVP) that cannot be bypassed without writer-side accumulation. Conclusion: ship XRP as v9.5.0-thin with conservative LIVE thresholds after GHOST validation. Don't fabricate the 90% pocket that isn't there.

09 · Lessons

Ten things learned.

L01 · MEMORY HYGIENE
The v2 box memo had a stale top paragraph.
A memory file with a correct addendum and an outdated lede is worse than a missing file. The lede gets quoted, the addendum gets skipped. Fix: invert the structure. If a box is dead, the first paragraph of its deploy memo should be "DECOMMISSIONED — DO NOT DEPLOY HERE."
Fixed in memory
L02 · NO AUTO-PROMOTE
The hand-driven LIVE rule earned its keep.
Three new strategies trained, three new probability emitters deployed, zero promoted to LIVE without explicit Billy approval. The allowlist hook caught the v2-box redirect attempt. The GHOST default in YAML caught the strategies. The pattern works. Every flip was hand-done; nothing escaped.
Held the line
L03 · DOCKER COMPOSE
On classifier-gpu, both files. Always.
docker-compose.yml alone gives a CPU-profile container that boots, emits, and silently misses the GPU declarations from docker-compose.gpu.yml. The override is non-optional. Deploy script gets a guard: compose -f base -f gpu, no exceptions.
Guard added
L04 · DISK HYGIENE
99% full is a silent killer.
pip install does not raise on partial writes when disk fills mid-install. The package looks installed. The python import fails with ModuleNotFoundError only at runtime. classifier-gpu now needs a weekly docker image prune cron + a disk-pressure alert at 80%. Thirteen stale image tags is two months of debt.
Routine prune scheduled
L05 · DATA INFRA
DuckDB + psql COPY > asyncpg for big pulls.
Above ~100k rows, asyncpg through SSM stalls invisibly. The hybrid pattern — DuckDB on the daily S3 parquet for bulk, psql COPY in 2h chunks for the delta — finishes in seconds what asyncpg can't finish in tens of minutes. New default.
Pattern adopted
L06 · OPTUNA RESUMABILITY
The SQLite study survived worker crashes.
The XRP Optuna study (40 trials over 9 minutes) had two worker crashes mid-run from asyncpg artefacts still on the host. The SQLite study DB at /tmp/xrp_v9_5_cache/optuna_study.db persisted every completed trial. Resumed each time without losing work. Use SQLite storage, not in-memory, for any non-trivial Optuna.
Default storage = sqlite
L07 · PER-WINDOW vs PER-TICK
WR per tick lies. WR per window is honest.
v9.2 BTC's 95% headline was a per-window number on too few windows. v9.3's 91.3% is a per-window number on enough windows. Per-tick WR can look 5-10pp higher because winning windows fire many ticks. Dedup before reporting. The walk-forward CV forced this dedup; it's now the default.
Per-window default
L08 · SHALLOW + BAGGY
max_depth=2 + heavy bagging is universal.
Both BTC's and XRP's Optuna best trials picked max_depth ≤ 2 and bagging in the 0.74-0.80 range with bagging_freq=1. The signal in both assets sits in a small number of shallow interactions; deep trees overfit per-window noise. This is the LGB-on-microstructure fingerprint — not an asset coincidence.
Universal pattern
L09 · ASYMMETRIC REWEIGHTING
XRP wants 1.5×, ETH wants 3.0×.
ETH's base UP rate is asymmetric — down_reweight=3.0 helps. XRP's base UP rate is 49.2% (well-balanced). Trials with dr ≥ 3.0 on XRP scored worse than dr=1.0/1.5. Stop applying ETH's reweighting wholesale; tune per-asset.
Per-asset tuning
L10 · LOADER GAP
9 features have no engine emitter — for ETH AND XRP.
binance_depth_* (4) and clob_pre_* (5) are trained-on but not served-on for both ETH and XRP. LGB's missing-value leaf handles the gap, but the model's feature importance shows these features carry signal. ETH's loader-side PR (#158) covers the None-fill, but the engine-side emitter doesn't exist for either asset yet. Ceiling is bounded until that ships.
Follow-up PR queued
